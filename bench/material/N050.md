# Procurement policy and data: instructions for the analytics assistant

This space answers questions about purchase requests, cost centres, approvals and vendors. It contains 50 rules and 30 claims. The data is in DuckDB; use the `sql` tool (read-only). Cite rule and claim ids (R…, G…, C…, H…) for every conclusion you draw from them.

## 1 Data model

### Table `cc`

A cost centre: a node of the budget tree, with its spending cap and the spend booked directly on it this quarter.

| column | type | meaning |
|---|---|---|
| `id` | id | Cost centre id. |
| `parent` | id | Parent cost centre; empty for the root. |
| `level` | int | Depth in the tree; the root is 0. |
| `org_unit` | enum | Organisational unit the centre belongs to. |
| `booked` | int | Spend booked directly on this centre (not its descendants). |
| `cap` | int | Spending cap of the centre this quarter. |

### Table `emp`

An employee, their role, their cost centre as finance records it, and their direct manager.

| column | type | meaning |
|---|---|---|
| `id` | id | Employee id. |
| `role` | enum | Role; governs the approval limit. |
| `cc` | id | Current cost centre in the finance system. |
| `manager` | id | Direct manager; empty for the vp. |
| `violation` | bool | The employee has a recorded policy violation. |

### Table `req`

A purchase request, raised on a date by an employee, for an amount, category and vendor.

| column | type | meaning |
|---|---|---|
| `id` | id | Request id. |
| `requester` | id | Employee who raised the request. |
| `amount` | int | Amount requested. |
| `category` | enum | Spend category (code list codes:category). |
| `vendor` | id | Vendor the purchase is from. |
| `date` | date | Date the request was raised; governs dated rules (R203). |
| `status` | enum | pending or cancelled. |
| `emergency` | bool | Flagged as an emergency. |

### Table `assignment`

A source's record (hr or finance) that an employee belongs to a cost centre from the effective date on.

| column | type | meaning |
|---|---|---|
| `emp` | id | Employee. |
| `cc` | id | Cost centre. |
| `source` | enum | hr or finance. |
| `effective` | date | Effective from. |

### Table `role_limit_version`

A dated version of a role's approval limit, valid from and to the given dates inclusive.

| column | type | meaning |
|---|---|---|
| `role` | enum | Role. |
| `limit` | int | Approval limit. |
| `valid_from` | date | First day valid. |
| `valid_to` | date | Last day valid. |

### Table `vendor_status`

A vendor's status during a period, from and to the given dates inclusive.

| column | type | meaning |
|---|---|---|
| `vendor` | id | Vendor. |
| `status` | enum | approved or suspended. |
| `valid_from` | date | First day. |
| `valid_to` | date | Last day. |

### Code lists

- `category`: software, hardware, services, capital
- `vendor_status`: approved, suspended
- `role`: analyst, manager, senior_manager, director, vp
- `request_status`: pending, cancelled
- `source`: hr, finance
- taxonomy of `category`: opex = software, services; capex = hardware, capital

## 2 Glossary

Business terms, each with its owner. Use the term the owner defines; resolve ambiguous ones before use.

- **booked total** (also: total booked, booked spend), owner finance: The booked total of a cost centre, as opposed to its booked amount, differs in counting the bookings of every descendant centre, not only those made directly on it.
- **booked amount** (also: direct booking), owner finance: The booked amount of a cost centre, as opposed to its booked total, is only what is booked directly on that centre.
- **committed spend** (also: commitments), owner finance: Committed spend, as opposed to booked total, differs in whether pending requests count. Finance has not decided which; no rule defines it.
- **headroom** (also: remaining budget), owner finance: Headroom, as opposed to cap, is what remains of the cap after the booked total (R105).
- **pending exposure** (also: pending total), owner finance: Pending exposure, as opposed to booked total, sums requests not yet booked (pending, not cancelled).
- **cost centre** (also: cc, budget centre), owner finance: A cost centre, as opposed to an org unit, is a node of the budget tree: caps and bookings roll up along it.
- **org unit** (also: organisational unit, unit), owner hr: An org unit, as opposed to a cost centre, is a flat grouping of centres (delivery, support, leadership); nothing rolls up along it.
- **department**, owner hr: Used in practice for both a cost centre and an org unit; resolve to one of them before use. See term:cost_centre, term:org_unit.
- **approval limit** (also: signing limit), owner procurement: A role's approval limit, as opposed to a cap, bounds a single request an approver may sign, not a centre's spend; dated (R202, R203).
- **vendor status**, owner procurement: A vendor's status, as opposed to its fitness claims, is the dated register entry (approved or suspended).
- **purchase request** (also: request, requisition), owner procurement: A purchase request, as opposed to a booking, is spend not yet committed.
- **capitalisation**, owner controller: Capitalisation, as opposed to expensing, books a request as an asset; owners may disagree per policy.
- **centre tag**, owner facilities: A centre tag, as opposed to an org unit, marks cost centres taking part in a facilities initiative.
- **on-time delivery**, owner operations: On-time delivery is operations' claim that a vendor delivers on schedule; it supports, but does not decide, qualification.
- **export licence**, owner legal: An export licence is the claim that a vendor holds the licence; legal and compliance may disagree, legal prevails.
- **supplier insurance**, owner risk: Supplier insurance is risk's claim that a vendor's insurance is valid.
- **employee perk**, owner hr: An employee perk, as opposed to an approval right, is a benefit granted by role.
- **programme clearance**, owner procurement: Programme clearance, as opposed to approval, says a request may be charged to a programme: within its limit and past the vendor check, subject to the programme's exceptions.
- **programme limit**, owner procurement: A programme limit, as opposed to a role's approval limit, bounds a single request under one spending programme; dated versions, the one valid on the request date governs.
- **quality audit**, owner compliance: A quality audit is compliance's claim that a vendor passed the audit.
- **qualified supplier**, owner procurement: A qualified supplier, as opposed to an approved vendor in the register, is procurement's claim that a vendor may be used under a supplier list, resting on insurance and quality claims.

## 3 How the rules combine

Read this before using any rule. The rules below are the policy. Where the rules and the data seem to disagree, the rules win.

- **Strict** rules always hold when their conditions hold. **Defeasible** rules hold unless a rule that *prevails over* them says otherwise. **Defeaters** block a conclusion and never establish one.
- A rule **prevails over** another only where this is stated ("Prevails over …", or a precedence rule naming the asserters). A conclusion holds when a rule supporting it applies and every rule against it that applies is overridden by a prevailing supporter.
- If rules for and against a conclusion both apply and neither prevails, the conclusion is **contested**. Report it as contested, with both sides. Do not pick one, and do not count it as true or as false. Anything that depends on a contested conclusion is contested as well.
- An **incompatibility** says two conclusions never both hold. If both are derived, the result is contested.
- **Dated rules and data:** a version or status applies on the date it is valid. For a request, that is the request date, unless the rule says otherwise. A view "as it stood at" a date evaluates every dated rule, status and claim at that date.
- **Claims** are statements by an asserter about an asset, each valid from–to.
  - A later claim by the **same** asserter supersedes an earlier conflicting one.
  - Claims by **different** asserters that conflict stay contested, unless a precedence rule orders the asserters.
  - A claim that *depends on* sub-claims fails if a required sub-claim fails. If a *supporting* sub-claim fails, the claim still holds but is qualified.
  - A claim outside its validity window does not hold.
- **Absence:** a "no" that rests only on not finding something in the data is a no *over the known facts*. Say so, unless a completeness claim covers the data. Booked totals are declared complete (claim C10).
- **Terms** without a definition are undecided: ask, or show each reading. Do not choose one silently.

## 6 Example queries

The semantic layer's definitions, written as SQL over the tables above. Parameters are shown with example values.

**entity:request**: Purchase requests.

```sql
SELECT id, requester, amount, category, vendor, date, status, emergency FROM req
```

**entity:employee**: Employees.

```sql
SELECT id, role, cc, manager, violation FROM emp
```

**dim:cost_centre**: The cost centre dimension: the budget tree, its caps and direct bookings.

```sql
SELECT id, parent, level, org_unit, booked, cap FROM cc
```

**dim:org_unit**: The organisational-unit dimension: a grouping of cost centres, not a tree.

```sql
SELECT org_unit AS id, CAST(COUNT(*) AS INTEGER) AS centres FROM cc GROUP BY org_unit
```

**hier:ancestors_or_self**: A cost centre and every ancestor up to the root (the centres a request is charged against).

```sql
WITH RECURSIVE up(cc, id, parent, depth) AS (SELECT id, id, parent, 0 FROM cc WHERE id IN ('cc0001') UNION ALL SELECT u.cc, c.id, c.parent, u.depth + 1 FROM cc c JOIN up u ON c.id = u.parent) SELECT cc, id AS anc, depth FROM up
```

**hier:subtree**: A cost centre and all its descendants.

```sql
WITH RECURSIVE sub(root, id) AS (SELECT id, id FROM cc WHERE id IN ('cc0001') UNION ALL SELECT s.root, c.id FROM cc c JOIN sub s ON c.parent = s.id) SELECT root, id FROM sub
```

**hier:reporting_chain**: An employee's manager, the manager's manager, and so on; not the employee.

```sql
WITH RECURSIVE ch(emp, approver, depth) AS (SELECT id, manager, 1 FROM emp WHERE id IN ('e077') AND manager IS NOT NULL UNION ALL SELECT ch.emp, e.manager, ch.depth + 1 FROM emp e JOIN ch ON e.id = ch.approver WHERE e.manager IS NOT NULL) SELECT ch.emp, ch.approver, emp.role, ch.depth FROM ch JOIN emp ON emp.id = ch.approver
```

**entity:request_in_subtree**: Requests whose requester's cost centre lies in the subtree of a root.

```sql
WITH RECURSIVE sub(root, id) AS (SELECT id, id FROM cc WHERE id IN ('cc0001') UNION ALL SELECT s.root, c.id FROM cc c JOIN sub s ON c.parent = s.id) SELECT sub.root, r.id, r.requester, e.cc, r.amount, r.status FROM req r JOIN emp e ON e.id = r.requester JOIN sub ON sub.id = e.cc
```

**entity:assignment**: hr and finance cost-centre assignment records.

```sql
SELECT emp, cc, source, effective FROM assignment
```

**measure:booked_total**: Sum of the spend booked directly on every cost centre in the subtree of a centre (zero where nothing is booked).

```sql
WITH RECURSIVE sub(root, id) AS (SELECT id, id FROM cc WHERE id IN ('cc0001') UNION ALL SELECT s.root, c.id FROM cc c JOIN sub s ON c.parent = s.id) SELECT sub.root AS cc, CAST(COALESCE(SUM(cc.booked), 0) AS BIGINT) AS value FROM sub JOIN cc ON cc.id = sub.id GROUP BY sub.root
```

**measure:pending_exposure**: Sum of the amounts of pending requests whose requester's cost centre lies in the subtree of a centre.

```sql
WITH RECURSIVE sub(root, id) AS (SELECT id, id FROM cc WHERE id IN ('cc0001') UNION ALL SELECT s.root, c.id FROM cc c JOIN sub s ON c.parent = s.id) SELECT sub.root AS cc, CAST(COALESCE(SUM(r.amount), 0) AS BIGINT) AS value FROM sub LEFT JOIN emp e ON e.cc = sub.id LEFT JOIN req r ON r.requester = e.id AND r.status = 'pending' GROUP BY sub.root
```
