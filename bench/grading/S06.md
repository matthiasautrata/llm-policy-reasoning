## Component: “Unapprovable requests” (no qualified approver in the reporting chain)

**Definition.** A pending request is *unapprovable* when nobody in the requester’s reporting chain holds a governing approval limit ≥ the request amount. Rests on:
- **R301** — has an approver iff someone in the requester’s reporting chain has a governing limit ≥ the amount (defeasible, no defeater stated);
- **R202 / R203** — the limit that counts is the version valid on the **request date**, not today’s (manager is 25,000 to 2026‑07‑31, 40,000 from 2026‑08‑01; analyst 5,000; senior_manager 50,000; director 100,000; vp 500,000);
- **R308** — eligibility requires an approver, so with no approver R310 can never fire (R311 auto‑approval is the only route left, and it needs software < 10,000).

**SQL** (scoped to the cc0049 subtree; the semantic layer defines “in subtree” via the requester’s `emp.cc`, per `entity:request_in_subtree`):

```sql
WITH RECURSIVE sub(root,id) AS (
  SELECT id,id FROM cc WHERE id='cc0049'
  UNION ALL SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id),
pending AS (
  SELECT r.id, r.requester, r.amount, r.category, r.vendor, r.date, r.emergency, e.cc, e.role, e.manager
  FROM req r JOIN emp e ON e.id=r.requester JOIN sub ON sub.id=e.cc
  WHERE r.status='pending'),
ch AS (
  SELECT p.id AS req, e.manager AS approver, 1 AS depth
  FROM pending p JOIN emp e ON e.id=p.requester WHERE e.manager IS NOT NULL
  UNION ALL
  SELECT ch.req, e.manager, ch.depth+1 FROM ch JOIN emp e ON e.id=ch.approver WHERE e.manager IS NOT NULL),
appr AS (
  SELECT ch.req, ch.approver, ch.depth, e.role, rlv."limit" AS lim
  FROM ch JOIN pending p ON p.id=ch.req JOIN emp e ON e.id=ch.approver
  JOIN role_limit_version rlv
    ON rlv.role=e.role AND p.date BETWEEN rlv.valid_from AND rlv.valid_to),
qual AS (
  SELECT a.req, COUNT(*) AS n_appr
  FROM appr a JOIN pending p ON p.id=a.req WHERE a.lim >= p.amount GROUP BY a.req)
SELECT p.id, p.requester, p.amount, p.category, p.vendor, p.date, p.emergency
FROM pending p LEFT JOIN qual q ON q.req=p.id
WHERE COALESCE(q.n_appr,0)=0
ORDER BY p.amount DESC;
```

**Caveats.**
- This is a **no over the known facts** (R301 is defeasible and there is no completeness claim on the org chart/`emp.manager`, unlike booked totals C10): a chain entry missing from `emp` would hide an unapprovable request.
- **Scoping is the dated question.** The figures use the requester’s current finance cost centre (`emp.cc`), as the semantic layer’s `entity:request_in_subtree` does. Re-scoping to the cost centre in force on the request date (assignment records, finance prevailing per **R313**) would move 16 requests out of the subtree and 11 in (425 → 420). In-subtree hr/finance disagreements (e.g. e10375: hr cc1663 from 2026‑06‑20 vs finance cc0291) resolve to finance by **R313** and stay in scope.
- Limits are taken at the request date (**R203**), so pre‑2026‑08‑01 requests are judged against the manager limit of 25,000; if the dashboard ever used today’s limits, several manager-signed requests would wrongly appear unapprovable.
- An unapprovable request is not the same as “not approved”: in this subtree the 336 not-approved requests all fail on cap breach (333), vendor suspension (89) or requester violation (10), not on approver availability — those are separate components.

## Report: “Why pending requests are not approved” + ageing

Scope: pending requests of **cc0049 + subtree** — 425 requests, 18,092,000, scoped via the requester’s `emp.cc` (`entity:request_in_subtree`). Ageing = **2026‑09‑15 − `req.date`** in calendar days.

**Rule ids used:** R106 (cap breach: amount + booked total of the requester’s centre or an ancestor > cap), R104/R105 (booked total rolls up; headroom), C10 (booked totals complete), R301 (has approver), R304 (cap check), R305 (vendor check), R306/R307 + R112 (emergency waiver; blocked for big capital), R308 (eligible), R309 (denied if requester has a recorded violation), R310/R311/R312 (approved; auto-approval), R314 (denial vs approval = incompatibility), R202/R203 (limits at request date).

### Component A — Reason breakdown (mutually exclusive, precedence: approver → cap → vendor → violation)

```sql
WITH RECURSIVE sub(root,id) AS (
  SELECT id,id FROM cc WHERE id='cc0049'
  UNION ALL SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id),
pending AS (
  SELECT r.id, r.requester, r.amount, r.category, r.vendor, r.date, r.emergency, e.cc, e.violation
  FROM req r JOIN emp e ON e.id=r.requester JOIN sub ON sub.id=e.cc WHERE r.status='pending'),
bt AS (  -- R104: booked total of every centre (C10 complete)
  WITH RECURSIVE s(root,id) AS (SELECT id,id FROM cc UNION ALL SELECT s.root,c.id FROM cc c JOIN s ON c.parent=s.id)
  SELECT s.root AS cc, CAST(SUM(cc.booked) AS BIGINT) AS booked_total FROM s JOIN cc ON cc.id=s.id GROUP BY s.root),
anc AS (SELECT id AS home, id AS anc, 0 AS depth FROM cc
        UNION ALL SELECT a.home, c.parent, a.depth+1 FROM anc a JOIN cc c ON c.id=a.anc WHERE c.parent IS NOT NULL),
breach AS (SELECT p.id FROM pending p JOIN anc a ON a.home=p.cc JOIN cc c ON c.id=a.anc JOIN bt ON bt.cc=a.anc
           WHERE p.amount+bt.booked_total > c.cap GROUP BY p.id),                      -- R106
ch AS (SELECT p.id AS req, e.manager AS approver, 1 AS depth FROM pending p JOIN emp e ON e.id=p.requester WHERE e.manager IS NOT NULL
       UNION ALL SELECT ch.req, e.manager, ch.depth+1 FROM ch JOIN emp e ON e.id=ch.approver WHERE e.manager IS NOT NULL),
appr AS (SELECT ch.req, ch.approver, ch.depth, e.role, rlv."limit" AS lim
         FROM ch JOIN pending p ON p.id=ch.req JOIN emp e ON e.id=ch.approver
         JOIN role_limit_version rlv ON rlv.role=e.role AND p.date BETWEEN rlv.valid_from AND rlv.valid_to), -- R202/R203
qual AS (SELECT a.req, COUNT(*) AS n_appr FROM appr a JOIN pending p ON p.id=a.req WHERE a.lim>=p.amount GROUP BY a.req), -- R301
c AS (SELECT p.*, COALESCE(q.n_appr,0) AS n_appr,
        EXISTS(SELECT 1 FROM breach b WHERE b.id=p.id) AS cap_breach,                  -- R304 fails
        (p.category='capital' AND p.amount>50000) AS big_capital,                      -- R112
        EXISTS(SELECT 1 FROM vendor_status v WHERE v.vendor=p.vendor AND v.status='approved'
               AND p.date BETWEEN v.valid_from AND v.valid_to) AS v_appr,              -- R204/R305
        (p.category='software' AND p.amount<10000) AS auto, p.violation AS denied,     -- R311 / R309
        DATE_DIFF('day', p.date, DATE '2026-09-15') AS days_waiting
      FROM pending p LEFT JOIN qual q ON q.req=p.id)
SELECT
  CASE WHEN auto AND denied THEN 'contested (R312 vs R309/R314)'
       WHEN (n_appr>=1 AND NOT cap_breach AND (v_appr OR (emergency AND NOT big_capital)) AND NOT denied) OR auto THEN 'approved'
       WHEN cap_breach AND NOT (v_appr OR (emergency AND NOT big_capital)) THEN 'not approved: cap breach + vendor suspended'
       WHEN cap_breach THEN 'not approved: cap breach'
       WHEN NOT (v_appr OR (emergency AND NOT big_capital)) THEN 'not approved: vendor suspended'
       WHEN denied THEN 'not approved: requester violation'
       ELSE 'other' END AS outcome,
  COUNT(*) AS n, CAST(SUM(amount) AS BIGINT) AS amount,
  MIN(days_waiting) AS min_d, CAST(ROUND(MEDIAN(days_waiting)) AS INT) AS med_d, MAX(days_waiting) AS max_d
FROM c GROUP BY 1 ORDER BY n DESC;
```

| outcome | requests | amount | min / med / max days waiting |
|---|---|---|---|
| not approved: cap breach | 255 | 13,010,000 | 0 / 61 / 106 |
| not approved: cap breach + vendor suspended | 63 | 3,750,000 | 0 / 49 / 106 |
| not approved: vendor suspended | 15 | 249,000 | 10 / 82 / 103 |
| not approved: requester violation | 3 | 23,000 | 42 / 76 / 79 |
| **contested** (auto-approve R312 vs denial R309/R314) | **1** | 3,000 | 97 / 97 / 97 |
| *(approved — reference)* | *88* | *1,057,000* | *2 / 70 / 106* |
| **not approved or contested, total** | **337** | **17,035,000** | 0 / 62 / 106 |

**Non-exclusive reason counts** (a request can have several blockers), same 337:
no approver **0** · cap breach **318** · vendor suspended **78** · requester violation **10** (cap+violation 6; cap+vendor+violation 1).

### Component B — Ageing of the not-approved/contested set (337 requests)

```sql
SELECT CASE WHEN days_waiting<=30 THEN '0-30 d' WHEN days_waiting<=60 THEN '31-60 d'
            WHEN days_waiting<=90 THEN '61-90 d' ELSE '91+ d' END AS bucket,

```

### Caveats
- **The contested row is not a “no” and not a “yes”.** r085616 (e289, 3,000, software, cog, 2026‑06‑10) is auto-approved (R311→R312) and its requester is denied (R309); R314 declares these incompatible, so it is reported as contested and excluded from both the approved and the not-approved totals (336 + 1 = 337).
- **Auto-approval bypasses the other checks (R311).** 15 of the 88 approved requests breach a cap and 11 have a vendor suspended on the request date; they are approved because R311 applies “without further checks”, not because the blockers are absent. Reason counts therefore differ between the approved and not-approved populations (cap 333 vs 318, vendor 89 vs 78).
- **Emergency waiver:** R306 clears a suspended vendor for emergency requests, but R307 (prevailing over R306) blocks it for big capital requests (R112: capital > 50,000). In this subtree no not-approved request is an emergency non-big-capital one, so the waiver changes no outcome here.
- **No approver is a no over the known facts** (R301 defeasible; no completeness claim on the org chart, unlike C10 for bookings) — and it is 0 here.
- **Ageing is a dashboard convention, not policy:** the ruleset contains no SLA or ageing rule, so buckets are ours; age is calendar days from the request date.
- **Scoping:** figures use `emp.cc` (semantic-layer `entity:request_in_subtree`); re-scoping to the cost centre in force on the request date (assignment records, finance prevailing per R313) would move 16 requests out and 11 in (425 → 420).
- Cap maths relies on booked totals being complete (C10) and on R104 roll-up; headroom follows R105.

## View “as it stood at 2026‑07‑31” (end of July 2026)

**How the as‑at view is built.**
- **Population:** only requests that existed then — pending requests in the cc0049 subtree raised on or before 2026‑07‑31. **273 of the 425** current pending requests qualify; **152** were raised in August–September and are dropped.
- **Per‑request anchors stay at the request date**, because the rules say so explicitly: **R203** (governing limit = version valid on the request date, *not today’s*) and **R204** (vendor status on the request date). So per‑request outcomes for these 273 are unchanged; the as‑at date changes which requests exist and the values that are asked *without* a date (**R201**).
- **Undated fields are a caveat:** `req.status` is not dated in the model, so the subset is “today’s pending, raised by end July” — a request cancelled after July would be wrongly retained.

### The three dated facts as at 2026‑07‑31

```sql
SELECT 'manager limit @2026-07-31' AS fact, CAST("limit" AS VARCHAR) AS value
  FROM role_limit_version WHERE role='manager' AND DATE '2026-07-31' BETWEEN valid_from AND valid_to
UNION ALL SELECT 'manager limit @today', CAST("limit" AS VARCHAR)
  FROM role_limit_version WHERE role='manager' AND DATE '2026-09-15' BETWEEN valid_from AND valid_to
UNION ALL SELECT 'bolt status @2026-07-31', status
  FROM vendor_status WHERE vendor='bolt' AND DATE '2026-07-31' BETWEEN valid_from AND valid_to
UNION ALL SELECT 'bolt status @today', status
  FROM vendor_status WHERE vendor='bolt' AND DATE '2026-09-15' BETWEEN valid_from AND valid_to;
```

| fact | at 2026‑07‑31 | today (2026‑09‑15) |
|---|---|---|
| **manager approval limit** | **25,000** (version 2026‑01‑01 → 2026‑07‑31) | 40,000 (version from 2026‑08‑01) |

- **The as‑at date does not retro‑change per‑request outcomes.** R203/R204 anchor limits and vendor status to the request date; only the population and the undated questions change. If you *did* freeze the vendor register at 2026‑07‑31 for every request (contrary to R204), the 17 pre‑July dyne requests would clear and vendor failures would fall from 43 to 26 (fern only).

## Gold reasons

- **GR1** (turns 1): An approver is anyone in the requester's reporting chain with a high enough limit, not only the direct manager
- **GR2** (turns 1, 4): The limit that counts is the version valid on the request date; a later limit change does not reclassify old requests
- **GR3** (turns 1): Software requests under 10,000 are approved automatically, without an approver: a separate path, not attributed to anyone
- **GR4** (turns 3): Approved means eligible (approver, cap check, vendor check) and not denied; reasons co-occur, so a breakdown allows several reasons per request, not one bucket
- **GR5** (turns 3): Denied (a recorded policy violation, owned by compliance) is a different reason from not eligible (procurement, finance)
- **GR6** (turns 1, 3): A request both denied and auto-approved is a conflict: show it as contested, in neither column
- **GR7** (turns 3): A cap failure may come from an ancestor centre's cap, not the requester's own
- **GR8** (turns 3): Vendor check on the request date; emergency requests pass despite a suspended vendor, except big capital requests (R307 overrides the waiver)
- **GR9** (turns 1, 4): The reporting chain depends on where the requester sits on the request date (e077 moved; hr and finance disagree, finance prevails)
- **GR10** (turns 3): "How long waiting" is not defined by any rule (no SLA, no start event): ask, or state the assumption; do not invent one silently
- **GR11** (turns 2): "Nobody can approve" is a negative answer over known facts (chains and limits are not declared complete): label it
- **GR12** (turns 4): Period-end view needs "as of" throughout (limits, vendor status, chain), not today's data filtered by date
