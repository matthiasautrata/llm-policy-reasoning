## Report component: “No-approver exceptions”

**Definition.** Pending requests for which the engine cannot find any approver in the requester’s reporting chain whose role limit is at least the request amount:

```clojure
[:has_approver "<request-id>"]
```

**Rules / claims it rests on**

| Rule | Role |
|---|---|
| **R301** | `has_approver` — a reporting-chain approver exists whose governing limit covers the amount |
| **R203** | `governing_limit` — binds the request to the approver role’s limit |
| **R202** | `limit_on` — role limit effective on the request date from `role_limit_version` |

Owner reported by the engine: **procurement**. No G/C/H claims are used for this component.

**Engine call.** For each pending request `r` in the cc0049 subtree, evaluate:

```clojure
(decide [:has_approver r] :as-of 2026-09-15)
```

A `false` result is the exception row. The drill-through table shows: request id, requester, amount, request date, cost centre, reporting-chain approver roles, and the highest applicable limit.

**Figure for cc0049**

| Scope | Pending requests | `has_approver = false` |
|---|---:|---:|
| **cc0049 itself** | 8 | **0** |
| cc0049 subtree | 425 | **0** |
| cc0289 | 56 | 0 |
| cc0290 | 53 | 0 |
| cc0291 | 66 | 0 |
| cc0292 | 62 | 0 |
| cc0293 | 58 | 0 |
| cc0294 | 68 | 0 |
| cc0295 | 54 | 0 |

So the “requests nobody can approve” list is **empty** for cc0049 and its subtree.

**Why the figure is zero.** I ran `has_approver` on the maximum-amount pending request of each of the 95 requesters in the subtree. All 95 returned `ANSWER true` (owner `procurement`), e.g.:

- `[:has_approver "r028134"]` → `true` — cc0049, 90,000, chain reaches `vp`
- `[:has_approver "r004511"]` → `true` — cc0289, 90,000, manager requester
- `[:has_approver "r049777"]` → `true` — cc0295, 120,000, analyst requester

Since `has_approver` is monotone in amount, if the maximum-amount request for a requester has an approver, all smaller requests by that requester do too. The chain check also shows all 95 requesters have a chain containing `vp`; the `vp` limit under R202 is 500,000 for 2026-01-01 to 2026-12-31, and the maximum pending amount in the subtree is 120,000.

**Caveats**

- `has_approver` only says *someone* in the chain has enough limit. It does **not** mean the request is approvable: **R304/R106** (`cap_ok`/`cap_breach`), **R305/R204** (`vendor_cleared`), and **R309** (`denied`) can still block it.
- The `vp` approver is outside the cc0049 subtree. If “nobody can approve” is intended to mean “nobody inside cc0049 or its child centres can approve”, that is a different metric and will be much larger, because many requests exceed the local manager limits.
- R301 uses the reporting chain from `emp.manager` and the role limit effective on the **request date** via R203/R202. The figure is unchanged at today’s date because the `vp` limit is constant over 2026.

## Report shown as at **2026-07-31** (end of July)

Set the report’s as-of control to `2026-07-31`. For date-scoped rules, the engine must also be given the relevant date argument (or the request’s own date); the `as_of` parameter alone does not re-date a request-bound rule.

### 1. Manager approval limit

**Engine call**

```clojure
(decide [:limit_on "manager" "2026-07-31" ?l] :as-of 2026-07-31)
```

**Figure:** `25000`

**Rules / owners:** **R202** (`limit_on`), **R203** (`governing_limit`); owner **procurement**.

**Caveat:** 2026-07-31 is the last day of the 25,000 manager limit. From 2026-08-01 the limit is 40,000 (`[:limit_on "manager" "2026-08-01" ?l]` → `40000`). Requests dated in July are assessed at 25,000; August requests at 40,000.

### 2. Register status of vendor bolt

**Data / engine basis**

```sql
SELECT status
FROM vendor_status
WHERE vendor = 'bolt'
  AND '2026-07-31' BETWEEN valid_from AND valid_to;
```

**Figure:** `approved`

The `vendor_status` row is `bolt / approved / 2026-01-01..2026-07-31`; the suspension row starts `2026-08-01`. Under **R204** (`vendor_status_for`) and **R305** (`vendor_cleared`), a bolt request dated on or before 2026-07-31 is vendor-cleared. For a bolt request dated 2026-08-01, the same rule returns `suspended` and `vendor_cleared = false`.

**Caveat:** **R204 is request-date-scoped, not `as_of`-scoped.** Passing `as_of 2026-07-31` to a request dated 2026-08-01 still evaluates the vendor at the request date. Use the vendor-status row above, or a request dated 2026-07-31, for the July register view. Also, `describe vendor:bolt` shows claim **C6** (`sanctioned bolt`) holding from 2026-06-01; that is a separate sanctions signal from the register status.

### 3. Cost centre of employee e077

**Engine call**

```clojure
(decide [:cost_centre_of "e077" ?cc] :as-of 2026-07-31)
```

**Figure:** `cc0077`

**Claims**

| Claim | Assertion | Standing at 2026-07-31 |
|---|---|---|
| **C4** | `cost_centre_of e077 cc0077` (finance, from 2026-01-01) | **holds** |
| **C3** | `cost_centre_of e077 cc0078` (hr, from 2026-07-01) | **rebutted** by C4 |
| **C5** | `cost_centre_of e077 cc0078` (finance, from 2026-08-01) | **not_in_force** |

**Caveat:** The finance and HR records disagree. At 2026-07-31 the finance January load **C4** prevails, so the answer is **cc0077**. From 2026-08-01, **C5** comes into force and **C3** holds, so the answer becomes **cc0078**.

### How this affects the rest of the dashboard

- **Approval-limit widgets** should read `limit_on` with the request’s date; for July requests the manager limit is 25,000, not 40,000.
- **Vendor-clearance widget** for bolt should show `approved` for July-dated requests and `suspended` from 2026-08-01. Emergency requests can still be cleared under **R306** when the vendor is suspended.
- **Waiting-time widget** should use **2026-07-31** as the reference date, not 2026-09-15.

## Gold reasons

- **GR1** (turns 1): An approver is anyone in the requester's reporting chain with a high enough limit, not only the direct manager
- **GR2** (turns 1, 4): The limit that counts is the version valid on the request date; a later limit change does not reclassify old requests
- **GR3** (turns 1): Software requests under 10,000 are approved automatically, without an approver: a separate path, not attributed to anyone
- **GR4** (turns 3): Approved means eligible (approver, cap check, vendor check) and not denied; reasons co-occur, so a breakdown allows several reasons per request, not one bucket
- **GR5** (turns 3): Denied (a recorded policy violation, owned by compliance) is a different reason from not eligible (procurement, finance)
- **GR6** (turns 1, 3): A request both denied and auto-approved is a conflict: show it as contested, in neither column
- **GR7** (turns 3): A cap failure may come from an ancestor centre's cap, not the requester's own
- **GR8** (turns 3): Vendor check on the request date; emergency requests pass despite a suspended vendor, except big capital requests (R307 overrides the waiver)
- **GR9** (turns 1, 4): The reporting chain depends on where the requester sits on the request date (e077 moved; hr and finance disagree, finance prevails)
- **GR10** (turns 3): "How long waiting" is not defined by any rule (no SLA, no start event): ask, or state the assumption; do not invent one silently
- **GR11** (turns 2): "Nobody can approve" is a negative answer over known facts (chains and limits are not declared complete): label it
- **GR12** (turns 4): Period-end view needs "as of" throughout (limits, vendor status, chain), not today's data filtered by date
