## Design change: parameterise the whole board by a *centre set*, not one centre

Everything below is the same five components as before, but each now takes a set of roots `S` (a multi‑select "centres I'm responsible for" control) plus an `as_of` date. Two mechanics make the set case safe:

- **Reduce `S` to its minimal elements.** Drop any root that is a descendant of another selected root, because a centre's figures are computed over its *subtree*. `{cc0009, cc0049}` → `{cc0009}` (cc0049 ⊂ cc0009). Summing both would double‑count.
- **Fan out, then union.** The engine goals (`booked_total`, `breach_in`, `approved_count`, …) take **one** root argument, so the board issues one call per minimal root and unions request ids / sums money. `request_in_subtree` (the fetch behind R110) is itself subtree‑scoped, so unioning the per‑root lists and de‑duping by `req.id` is exactly the union of subtrees.

Cap is **not** additive down the tree (cc0009's cap is 5,572,000; its six children's caps sum to 4,983,000), so for a selection the cap tile sums the caps of the *minimal selected roots only*.

### Caveats
1. **Nested selections must be de‑duplicated** — `{cc0009, cc0049}` collapses to `{cc0009}`; never add the two tiles.
2. **Cap is per node, not additive**; only sum caps over the minimal selected roots.
3. **Employees sit on non‑leaf centres** (e009 on cc0009, e049 on cc0049, …): the subtree scope must include the root node itself, else cc0009 under‑counts by 2 requests / 63,000.
4. **Scope uses `emp.cc`** (the finance system field) as in the `request_in_subtree` fetch — not the claim‑based `cost_centre_of` (claims C3/C4/C5 for e077 show hr vs finance disagreement). For these centres hr and finance agree, but flag it where they don't.
5. **`approved_count`/`approved_total` return CONFLICT** (R312 vs R314) for both cc0049 and cc0009 — render as "disputed", not a number.
6. All dated rules (R202/R204, R203 as_of) must be evaluated at the request's `date` for pipeline rows, and at the board `as_of` for the cap tiles.

## Component 8 — "Committed spend" tile: **governed term, but undefined — do not print a number**

**Engine check (run it, don't assume):**
- `resolve_term "committed spend"` → **concept** `term:committed_spend`, owner **finance**. Definition: *"Committed spend, as opposed to booked total, differs in whether pending requests count. Finance has not decided which; no rule defines it."*
- `decide [:committed_spend "cc0049" ?v]` → **UNDERDETERMINED** (known term, nothing defines it). `describe term:committed_spend` → `ANSWER`, doc as above, **no claims, no rules**.
- Contrast `[:committed_total "cc0049" ?v]` → **OUT_OF_SCOPE** (not even a known predicate).

So the honest board behaviour is: render the tile as **"Committed spend — definition pending (owner: finance)"**, greyed, with no single figure, and show the candidate readings the two definitions would produce, each resting on components you already have. Do **not** let the tile silently pick one.

**The readings, with cc0049's figures** (booked_total from R104 = 606,000; cap 787,000):

| reading | definition it assumes | components it adds | cc0049 figure | % of cap |
|---|---|---|---|---|
| A — pending excluded | "committed = booked" | `booked_total` (R104) only | **606,000** | 77.0 % |
| B — pending included (all) | "committed = booked + everything in flight" | R104 + `request_in_subtree(cc0049,pending)` | **606,000 + 18,092,000 = 18,698,000** | 2,376 % |
| C — pending included, PO only | "committed = booked + requests that became a commitment" | R104 + `po_issued` pending | **606,000 + 763,000 = 1,369,000** | 174 % |

- Reading **C** uses the nearest governed proxy for "in‑flight has hardened into a commitment": `po_issued` (R316) = `approved` (R310 ← `eligible` R308 ← `has_approver` R301 / `cap_ok` R304 / `vendor_cleared` R305 ← R204). For cc0049 that is **61 requests / 763,000** (SQL over the same rule bodies; verified per‑request e.g. `[:po_issued "r001711"]` = true, `[:po_issued "r000659"]` = false).
- Reading **B** is the literal "pending counts" reading and is a loose upper bound: it includes 333 requests / 16,845,000 that would breach (R110/R106), 10 / 416,000 denied (R309) and 114 / 5,028,000 on suspended vendors (R204/R305).

**Caveats**
1. **No rule defines committed spend** — any number you print is a local convention, not a governed one; the term is owned by **finance** and is exactly the open question "do pending requests count?". Escalate to finance rather than coding a choice into the tile.
2. Reading **C is itself tainted**: `approved_total`/`approved_count` for cc0049 return **CONFLICT** (R312 vs R314) — driven by **r085616** (software 3,000, requester has a violation: `[:approved …]` = CONFLICT, `[:po_issued …]` = CONFLICT). So "PO‑issued pending" is only a proxy, and one request in cc0049 cannot be classified.
3. All three readings must be recomputed per minimal root for a selection (Component 1's reduction rule); for `{cc0009, cc0049}` → `{cc0009}` the readings are 3,715,000 / 103,288,000 / 9,275,000 (booked 3,715,000 + eligible 5,560,000).
4. Whatever reading is chosen, keep it visibly separate from the **cap** tile: A leaves 181,000 headroom, B/C exceed the cap, so the same cost centre flips from "under" to "over" purely on the definition — which is why the term must be resolved before the tile goes live.

## Component 9 — `as_of` control ("as it stood at date D")

Add a board‑level date control defaulting to today; every dated rule/claim is then evaluated with `as_of = D`. For D = **2026‑07‑31** the two tiles you asked for resolve as follows.

### Tile A — Approval limit of a role (manager), as of 2026‑07‑31
- **Rules:** **R201** (`role_limit ?role ?l`) ← **R202** (`limit_on`), over `role_limit_version`, with the `valid_from ≤ D ≤ valid_to` window (owner: procurement).
- **Call:** `decide [:role_limit "manager" ?l]` with `as_of 2026-07-31` → **25,000** (verified via `why`: R201→R202, row `manager, 25000, 2026‑01‑01 … 2026‑07‑31`).
- **Figure:** **manager limit = 25,000 at 2026‑07‑31** (today, 2026‑09‑15, the same call returns **40,000**, row valid from 2026‑08‑01). The limit steps up the day after your cut‑off — the tile must show the version it used, not "the" limit.

### Tile B — Cost centre of employee e077, as of 2026‑07‑31
- **Claims:** **C4** (finance, `cost_centre_of e077 cc0077`, from 2026‑01‑01) — **holds**; **C3** (hr, `cost_centre_of e077 cc0078`, from 2026‑07‑01) — **rebutted**, defeated by C4 under **authority:R313**; **C5** (finance, `cost_centre_of e077 cc0078`, from 2026‑08‑01) — **not_in_force** at this date.
- **Calls:** `describe emp:e077 as_of 2026-07-31` and `decide [:cost_centre_of "e077" ?c] as_of 2026-07-31` → **cc0077** (`why`: the goal rests on claim C4, winner over C3 via authority R313).
- **Figure:** **e077 was in cc0077 at the end of July 2026** (the answer flips to cc0078 from 2026‑08‑01, when C5 comes into force and C3 holds).

### Caveats
1. **The defeat is date‑dependent, not a fixed fact.** Between 2026‑07‑01 and 2026‑07‑31 hr and finance disagree and *finance wins* (C4 defeats C3); from 2026‑08‑01 the finance posting C5 supersedes and both agree on cc0078. A dashboard that caches "e077 = cc0078" is wrong for July.
2. **Same hazard on the other dated tiles:** vendor status (R204/R305) also changes at 2026‑08‑01 — bolt goes approved→suspended, so a July board and a September board classify the same request differently; role limits change (R201/R202); and every claim's standing is recomputed. Always pass `as_of`.
3. **`cost_centre_of` (claims) vs `emp.cc` disagree.** `emp.cc` for e077 is still **cc0077** today, and the `assignment` rows are both cc0077 — yet the governed `cost_centre_of` today is cc0078. Component 3/4 scope pipeline rows by `emp.cc`, so e077's requests sit in cc0077's pipeline even though the governed answer is cc0078. Flag this on the board and use the claim‑based answer for anything employee‑attribution related.
4. **The cap/spend tiles are not dated by `as_of`:** `cc.booked`/`cc.cap` are "this quarter" snapshots with no history, so at D = 2026‑07‑31 the spend‑vs‑cap tiles can only show the current snapshot — label them "current quarter (not restated to D)".

## Gold reasons

- **GR1** (turns 1, 2): Booked total rolls up over the subtree; it is semi-additive across the hierarchy: never add a parent's and its children's totals
- **GR2** (turns 2): Headroom is cap minus booked total and non-additive: never sum headroom across centres
- **GR3** (turns 1): A request can breach a parent's cap while its own centre still has headroom: the cap check runs against the requester's centre and every ancestor
- **GR4** (turns 3): "Committed spend" is not defined: finance has not decided whether pending requests count. Show both readings or refuse the label; do not pick one silently
- **GR5** (turns 1, 4): The approval limit that governs a request is the version valid on the request date, not today's
- **GR6** (turns 1): Vendor status is taken on the request date; emergency requests pass despite a suspended vendor
- **GR7** (turns 1): Software requests under 10,000 are approved automatically, without the other checks; show them as their own segment
- **GR8** (turns 1): A request both denied and approved is a conflict (R314): show it as contested; it must not be counted in an approved total
- **GR9** (turns 1, 2): Employee cost centre: hr and finance disagree for e077; finance prevails by R313. Use finance's mapping, and show the dispute where R313 does not apply
- **GR10** (turns 4): A mid-year transfer (e077, cc0077 → cc0078): which centre a request counts for depends on the date
- **GR11** (turns 1): Booked totals are declared complete (C10); pending-pipeline figures rest on known facts only: label them
- **GR12** (turns 4): All dated policy needs an "as of" parameter; a period-end view is not today's view with a filter
- **GR13** (turns 2): A selection of centres is totalled over the union of their subtrees, not by adding their totals: a parent and its child selected together must not double-count
