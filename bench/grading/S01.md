# S01: task A1 (cost-centre spend dashboard)

Graded blind: the arm, model and N are in `index.json`, not here.

## Turn 1

> Build a dashboard so cost-centre managers can see their spend against their cap and the pipeline of pending requests. As a worked example, give each component's figures for cost centre cc0049.



## Turn 2

> Managers of parent centres want the same view. or filter / select the centres they want to see Give the figures for cc0009 (the parent of cc0049), and for a selection of cc0009 and cc0049 together.

I’m reusing the previous dashboard, with one new parameter: **`selected_centres`**. A manager sees their own centre by default; a parent can multi-select centres. The selection computes the **union of the selected centres’ subtrees, deduplicated**. If one selected centre is an ancestor of another, the descendant is counted once. This follows **R104** (booked total rolls up over the subtree) and **R105** (headroom is per centre: cap − booked total). Caps are node-specific, so the dashboard never sums caps across selected centres.

## Components and SQL

### Core parameterised SQL

Every request-level component below runs this core query, with `selected` changed per user selection.

```sql
WITH RECURSIVE
selected(id) AS (VALUES ('cc0009'),('cc0049')),  -- dashboard parameter
sub(root,id) AS (
  SELECT id,id FROM selected
  UNION
  SELECT sub.root,c.id FROM cc c JOIN sub ON c.parent=sub.id
),
unique_cc AS (SELECT DISTINCT id FROM sub),
chain(emp,approver,depth) AS (
  SELECT id,manager,1 FROM emp WHERE manager IS NOT NULL
  UNION ALL
  SELECT ch.emp,e.manager,ch.depth+1
  FROM emp e JOIN chain ch ON e.id=ch.approver
  WHERE e.manager IS NOT NULL
),
bt(root,id) AS (
  SELECT id,id FROM cc
  UNION ALL
  SELECT b.root,c.id FROM cc c JOIN bt b ON c.parent=b.id
),
booked AS (
  SELECT bt.root AS cc, CAST(COALESCE(SUM(c.booked),0) AS BIGINT) AS booked_total
  FROM bt JOIN cc c ON c.id=bt.id GROUP BY bt.root
),
anc(cc,anc,depth) AS (
  SELECT id,id,0 FROM cc
  UNION ALL
  SELECT a.cc,c.parent,a.depth+1
  FROM anc a JOIN cc c ON c.id=a.anc
  WHERE c.parent IS NOT NULL
),
rb AS (
  SELECT r.id, r.requester, r.amount, r.category, r.vendor, r.date, r.emergency,
         e.violation, e.cc AS requester_cc
  FROM req r JOIN emp e ON e.id=r.requester
  JOIN unique_cc u ON u.id=e.cc
  WHERE r.status='pending'
),
appr AS (
  SELECT rb.id,
         EXISTS (
           SELECT 1 FROM chain ch
           JOIN emp m ON m.id=ch.approver
           JOIN role_limit_version rlv
             ON rlv.role=m.role
            AND rb.date BETWEEN rlv.valid_from AND rlv.valid_to
           WHERE ch.emp=rb.requester
             AND rlv.limit >= rb.amount
         ) AS has_approver
  FROM rb
),
breach AS (
  SELECT DISTINCT rb.id, rb.amount
  FROM rb
  JOIN anc ON anc.cc=rb.requester_cc
  JOIN cc ON cc.id=anc.anc
  JOIN booked b ON b.cc=anc.anc
  WHERE rb.amount + b.booked_total > cc.cap
),
vs AS (
  SELECT rb.id, vs.status
  FROM rb
  LEFT JOIN vendor_status vs
    ON vs.vendor=rb.vendor
   AND rb.date BETWEEN vs.valid_from AND vs.valid_to
),
st AS (
  SELECT rb.id, rb.amount, rb.requester_cc, rb.violation,
         (rb.category='capital' AND rb.amount > 50000) AS big_capital,
         (rb.category='software' AND rb.amount < 10000) AS auto_approved,
         COALESCE(appr.has_approver,FALSE) AS has_approver,
         (breach.id IS NOT NULL) AS cap_breach,
         (COALESCE(vs.status='approved',FALSE)
          OR (rb.emergency AND vs.status='suspended'
              AND NOT (rb.category='capital' AND rb.amount > 50000))
         ) AS vendor_cleared
  FROM rb
  LEFT JOIN appr ON appr.id=rb.id
  LEFT JOIN breach ON breach.id=rb.id
  LEFT JOIN vs ON vs.id=rb.id
),
fin AS (
  SELECT *,
         (has_approver AND NOT cap_breach AND vendor_cleared) AS eligible,
         (violation) AS denied,
         ((has_approver AND NOT cap_breach AND vendor_cleared AND NOT violation)
          OR auto_approved) AS approved_proven,
         (auto_approved AND violation) AS approval_contested
  FROM st
)
SELECT * FROM fin;
```

### 1. Spend vs cap

**Rules/claims:** **R104**, **R105**, **C10**.

```sql
SELECT cc.id, cc.cap, b.booked_total,
       CAST(cc.cap-b.booked_total AS BIGINT) AS headroom,
       ROUND(100.0*b.booked_total/cc.cap,1) AS pct_used
FROM cc
JOIN unique_cc u ON u.id=cc.id
JOIN booked b ON b.cc=cc.id
ORDER BY cc.id;
```

## Caveats

- **Cost-centre resolution:** **R313** says finance prevails over hr. In the `cc0009` subtree, two employees conflict: `e10375` (hr `cc1663`, finance `cc0291`) and `e6935` (hr `cc1136`, finance `cc0295`). Using finance includes them under `cc0009`; using hr would remove 5 pending requests / 383,000 from the `cc0009` subtree. Claims **C3**–**C5** for `e077` are not in this subtree, but the same precedence rule applies.
- **Aggregate vs per-request breach:** **R106** is per request. The huge subtree pending exposure (99,173,000 for `cc0009`) is not itself a cap breach. Only the **R110** breach alert (1,865 requests / 92,409,000) is the policy conclusion.
- **Caps are node-specific:** do not sum caps across selected centres. For `{cc0009, cc0049}`, the effective top cap is `cc0009`’s 5,572,000; `cc0049`’s 787,000 is a sub-cap.
- **Approval is defeasible:** **R310** and **R312** are defeasible; **R314** makes a denied+auto-approved request **contested**. The 11 contested requests / 63,000 in `cc0009` are reported separately, not counted as approved. **R311** auto-approval bypasses further checks, so some approved software requests under 10,000 can carry vendor-fail or cap-breach flags. **R120**/**R121** answer over known facts only.
- **Dated rules:** role limits use the request date (**R202**, **R203**); vendor status uses the request date (**R204**). Today is 2026-09-15.
- **Vendor claims:** **C1**/**C6** (bolt) and **C2**/**C7** (cog) are fitness/benchmark claims. The glossary says vendor status is the dated register entry, so **R305** uses `vendor_status`, not those claims. Booked totals are complete by **C10**.

## Turn 3

> Can we show committed spend? Give the figure for cc0049.

Yes — but **not as one number**. The glossary says **committed spend** is owned by finance and that it “differs from booked total in whether pending requests count. Finance has not decided which; no rule defines it.” So the dashboard must show a **reading selector**, not silently pick one.

## Component: committed-spend tile

**Rules/claims:** glossary **committed spend** (finance, undecided), **booked total** (finance), **booked amount** (finance), **pending exposure** (finance); **R104** and **C10** for booked total; **R120**/**R121** and **R310**/**R312** for the approved-pending variant.

```sql
WITH RECURSIVE
sub(root,id) AS (
  SELECT id,id FROM cc WHERE id='cc0049'
  UNION ALL
  SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id
),
bt(root,id) AS (
  SELECT id,id FROM cc
  UNION ALL
  SELECT b.root,c.id FROM cc c JOIN bt b ON c.parent=b.id
),
booked AS (
  SELECT bt.root AS cc, CAST(COALESCE(SUM(c.booked),0) AS BIGINT) AS booked_total
  FROM bt JOIN cc c ON c.id=bt.id GROUP BY bt.root
),
pending AS (
  SELECT CAST(COALESCE(SUM(r.amount),0) AS BIGINT) AS pending_exposure
  FROM req r JOIN emp e ON e.id=r.requester
  JOIN sub ON sub.id=e.cc
  WHERE r.status='pending'
)
SELECT b.booked_total,
       p.pending_exposure,
       b.booked_total AS committed_pending_excluded,
       b.booked_total + p.pending_exposure AS committed_pending_included
FROM booked b, pending p
WHERE b.cc='cc0049';
```

For the approved-pending-only variant, add the approved total from the approval-pipeline SQL in the previous turn.

## Caveats

- **Do not use any of these as a cap-breach figure.** **R106** is per request; committed spend is an aggregate. The `cc0049` breach alert remains 333 requests / 16,845,000 from the previous turn.
- **Pending exposure** counts all pending, not cancelled, requests. **Approved pending only** is narrower and uses **R310**/**R312**; contested approvals (**R314**) are excluded from that total.
- If finance wants a single committed-spend number, it must first decide the two open choices: **whether pending requests count**, and **whether the scope is direct or subtree**.

## Gold reasons

- **GR1** (turns 1, 2): Booked total rolls up over the subtree; it is semi-additive across the hierarchy: never add a parent's and its children's totals
- **GR2** (turns 2): Headroom is cap minus booked total and non-additive: never sum headroom across centres
- **GR3** (turns 1): A request can breach a parent's cap while its own centre still has headroom: the cap check runs against the requester's centre and every ancestor
- **GR4** (turns 3): "Committed spend" is not defined: finance has not decided whether pending requests count. Show both readings or refuse the label; do not pick one silently
- **GR5** (turns 1, 4): The approval limit that governs a request is the version valid on the request date, not today's
- **GR6** (turns 1): Vendor status is taken on the request date; emergency requests pass despite a suspended vendor
- **GR7** (turns 1): Software requests under 10,000 are approved automatically, without the other checks; show them as their own segment
- **GR8** (turns 1): A request both denied and approved is a conflict (R314): show it as contested; it must not be counted in an approved total
- **GR9** (turns 1, 2): Employee cost centre: hr and finance disagree for e077; finance prevails by R313. Use finance's mapping, and show the dispute where R313 does not apply
- **GR10** (turns 4): A mid-year transfer (e077, cc0077 → cc0078): which centre a request counts for depends on the date
- **GR11** (turns 1): Booked totals are declared complete (C10); pending-pipeline figures rest on known facts only: label them
- **GR12** (turns 4): All dated policy needs an "as of" parameter; a period-end view is not today's view with a filter
- **GR13** (turns 2): A selection of centres is totalled over the union of their subtrees, not by adding their totals: a parent and its child selected together must not double-count
