## Component 1 — `vendor_fitness_claim_rollup`

**Purpose:** show each vendor’s root fitness claim, its required/supporting sub-claims, and whether it holds, fails, or holds qualified.

**Rests on:** claims **C1**, **C1.1**, **C1.2**, **C1.3**, **C6**, **C2**, **C2.1**, **C2.2**, **C2.3**, **C7**; the claim rules in §3 — validity window, same-asserter supersession, and required vs supporting sub-claims.

**SQL run:**

```sql
WITH claims(id, vendor, predicate, asserted_by, asserted_at, valid_from, valid_to, qualifier, backing, role) AS (
  VALUES
    ('C1','bolt','fit_for_use','procurement', DATE '2026-03-01', DATE '2026-01-01', DATE '2026-12-31','presumably','Vendor onboarding file VO-17','root'),
    ('C1.1','bolt','due_diligence_passed','compliance', DATE '2026-02-15', DATE '2026-01-01', NULL,'certainly','KYC review 2026-02','required'),
    ('C1.2','bolt','NOT_sanctioned','risk', DATE '2026-02-20', DATE '2026-01-01', DATE '2026-12-31','certainly','Sanctions screening run S-0220','required'),
    ('C1.3','bolt','price_within_benchmark','finance', DATE '2026-02-25', DATE '2026-01-01', NULL,'presumably','Benchmark B-12: within 5%','supporting'),
    ('C6','bolt','sanctioned','risk', DATE '2026-06-03', DATE '2026-06-01', NULL,'certainly','Sanctions list update 2026-06 (supersedes screening S-0220 for bolt)','conflict'),
    ('C2','cog','fit_for_use','procurement', DATE '2026-03-01', DATE '2026-01-01', DATE '2026-12-31','presumably','Vendor onboarding file VO-21','root'),
    ('C2.1','cog','due_diligence_passed','compliance', DATE '2026-02-15', DATE '2026-01-01', NULL,'certainly','KYC review 2026-02','required'),
    ('C2.2','cog','NOT_sanctioned','risk', DATE '2026-02-20', DATE '2026-01-01', DATE '2026-12-31','certainly','Sanctions screening run S-0220','required'),
    ('C2.3','cog','price_within_benchmark','finance', DATE '2026-02-25', DATE '2026-01-01', NULL,'presumably','Benchmark B-12: within 5%','supporting'),
    ('C7','cog','NOT_price_within_benchmark','finance', DATE '2026-05-10', DATE '2026-05-10', NULL,'certainly','Benchmark B-19: 12% above','conflict')
),
supersessions(earlier, later) AS (
  VALUES ('C1.2','C6'), ('C2.3','C7')
),
claim_status AS (
  SELECT c.*,
         (DATE '2026-09-15' BETWEEN c.valid_from AND COALESCE(c.valid_to, DATE '9999-12-31')) AS in_validity,
         s.later AS superseded_by,
         CASE WHEN (DATE '2026-09-15' BETWEEN c.valid_from AND COALESCE(c.valid_to, DATE '9999-12-31'))
                   AND s.later IS NULL
              THEN TRUE ELSE FALSE END AS base_holds
  FROM claims c
  LEFT JOIN supersessions s ON s.earlier = c.id
),
deps(claim, subclaim, kind) AS (
  VALUES
    ('C1','C1.1','required'), ('C1','C1.2','required'), ('C1','C1.3','supporting'),
    ('C2','C2.1','required'), ('C2','C2.2','required'), ('C2','C2.3','supporting')
),
root_eval AS (
  SELECT d.claim,
         BOOL_AND(CASE WHEN d.kind = 'required' THEN cs.base_holds ELSE TRUE END) AS required_ok,
         BOOL_AND(CASE WHEN d.kind = 'supporting' THEN cs.base_holds ELSE TRUE END) AS supporting_ok
  FROM deps d
  JOIN claim_status cs ON cs.id = d.subclaim
  GROUP BY d.claim
)
SELECT cs.id, cs.vendor, cs.predicate, cs.asserted_by, cs.role,
       CASE
         WHEN cs.role = 'root' AND NOT re.required_ok THEN 'does not hold (required sub-claim failed)'
         WHEN cs.role = 'root' AND re.required_ok AND NOT re.supporting_ok THEN 'holds but qualified (supporting sub-claim failed)'
         WHEN cs.base_holds THEN 'holds'
         ELSE 'does not hold'
       END AS standing_today,
       cs.superseded_by, cs.qualifier, cs.backing
FROM claim_status cs
LEFT JOIN root_eval re ON re.claim = cs.id
ORDER BY cs.vendor, cs.id;
```

**Worked-example figures:**

| Vendor | Claim | Standing today | Detail |
|---|---|---|---|
| bolt | C1 `fit_for_use` | does not hold | required C1.2 fails |
| bolt | C1.1 `due_diligence_passed` | holds | compliance, certainly |
| bolt | C1.2 `NOT_sanctioned` | does not hold | superseded by C6 |
| bolt | C1.3 `price_within_benchmark` | holds | supporting only; root still fails |
| bolt | C6 `sanctioned` | holds | risk, valid 2026-06-01→open |
| cog | C2 `fit_for_use` | holds but qualified | supporting C2.3 fails |
| cog | C2.1 `due_diligence_passed` | holds | compliance, certainly |
| cog | C2.2 `NOT_sanctioned` | holds | risk, certainly |
| cog | C2.3 `price_within_benchmark` | does not hold | superseded by C7 |
| cog | C7 `NOT_price_within_benchmark` | holds | finance, valid 2026-05-10→open |

**Caveats:**
- Claims are not in the DuckDB tables shown in the data model. The SQL above materialises the claim set as a CTE; in production this should read a maintained claim-ledger table.
- Supersession here is resolved because the conflicting claims have the **same asserter** (risk for C1.2/C6; finance for C2.3/C7). Different-asserter conflicts would be contested unless a precedence rule orders the asserters.
- Required sub-claim failure defeats the root claim; supporting sub-claim failure only qualifies it. That is why bolt fails and cog remains qualified.
- C1.3 still holds for bolt, but it cannot rescue C1 because C1.2 is required.
- Only bolt and cog have fitness claims in the claim set. Absence of a fitness claim for other vendors is not evidence of unfitness.

## Component 3 — `vendor_check_gate` (procurement action layer)

**Purpose:** show whether requests pass the vendor check on their own request date, including the emergency waiver and its big-capital exception.

**Rests on:** **R204** (status on request date), **R305** (pass vendor check if approved on request date), **R306** (emergency exception for suspended vendor), **R307** (emergency waiver does not apply to a big capital request; prevails over R306), **R112** (big capital = capital request over 50,000).

**SQL run (pending requests, bolt and cog):**

```sql
WITH req_vs AS (
  SELECT r.id, r.vendor, r.amount, r.category, r.emergency, r.date, r.status,
         vs.status AS vendor_status_on_date,
         (r.category = 'capital' AND r.amount > 50000) AS big_capital
  FROM req r
  LEFT JOIN vendor_status vs
    ON vs.vendor = r.vendor
   AND r.date BETWEEN vs.valid_from AND vs.valid_to
  WHERE r.vendor IN ('bolt','cog') AND r.status = 'pending'
)
SELECT vendor,
       COUNT(*) AS pending_requests,
       SUM(CASE WHEN vendor_status_on_date = 'approved' THEN 1 ELSE 0 END) AS approved_on_request_date,
       SUM(CASE WHEN vendor_status_on_date = 'suspended' AND emergency AND NOT big_capital THEN 1 ELSE 0 END) AS emergency_waived_R306,
       SUM(CASE WHEN vendor_status_on_date = 'suspended' AND emergency AND big_capital THEN 1 ELSE 0 END) AS emergency_blocked_R307,
       SUM(CASE WHEN vendor_status_on_date = 'suspended' AND NOT emergency THEN 1 ELSE 0 END) AS suspended_not_emergency
FROM req_vs
GROUP BY vendor
ORDER BY vendor;
```

**Worked-example figures — pending requests:**

| Vendor | Pending requests | Approved on request date | R306 emergency waived | R307 emergency blocked (big capital) | Suspended, not emergency |
|---|---:|---:|---:|---:|---:|
| bolt | 14,829 | 8,449 | 1,550 | 133 | 4,697 |
| cog | 15,004 | 15,004 | 0 | 0 | 0 |

**Caveats:**
- These figures are **pending** requests only. Across all requests, bolt has 16,537: 9,450 approved on date, 1,723 R306-waived, 147 R307-blocked, and 5,217 suspended-not-emergency; cog has 16,615, all approved on date.
- R307 is a defeater and prevails over R306, so emergency big-capital requests from a suspended vendor still fail the vendor check.
- R305 and R306 are defeasible; other prevailing rules could override them if present.
- The vendor check is only one eligibility condition. Approval also depends on the cap check and approver rules (**R308**, **R310**), and an automatic software approval can bypass checks under **R311** if that entitlement applies.

## Gold reasons

- **GR1** (turns 1): Fit for use is procurement's claim, resting on required sub-claims (due diligence, not sanctioned) and a supporting one (price within benchmark)
- **GR2** (turns 1, 2): A failing required sub-claim rebuts fitness; a failing supporting one only qualifies it
- **GR3** (turns 3): Each sub-claim has its own asserter (compliance, risk, finance) and validity; report them per claim, not under procurement
- **GR4** (turns 2, 4): cog: finance's later claim (C7, from 10 May) that the price is not within benchmark supersedes its earlier C2.3 (same asserter, later wins): fitness is qualified from that date
- **GR5** (turns 1, 4): bolt: risk's later claim (C6, sanctioned, from 1 June) supersedes its earlier C1.2: fitness rebutted from that date
- **GR6** (turns 2): Later wins only within one asserter; between different asserters a disagreement stays contested unless superiority is stated
- **GR7** (turns 1): Validity windows end (C1, C2 to 31 Dec): fitness expires; it is not permanent
- **GR8** (turns 4): "What we knew at <date>" (assertion and recording time) differs from "what held at <date>" (valid time): two axes, two views
- **GR9** (turns 1): Vendor status (register) is distinct from fitness claims: a vendor can be approved in the register yet not fit, and the reverse
