All figures below were run at `as_of 2026-09-15`. Engine answers are cited by rule id; SQL is used only for the row fetches the rules themselves declare, never to re-implement a rule.

## Turn 1 — Cost‑centre manager view (spend vs cap + pending pipeline)

### D1 · Scope header (per centre)
**Rests on:** R104 (`booked_total`), R105 (`headroom`), data row `cc`.
**Call:** `decide [:booked_total "cc0049" ?v]`, `decide [:headroom "cc0049" ?h]`, `SELECT cap FROM cc WHERE id='cc0049'`.
**Figures — cc0049:** cap **787,000**; booked total **606,000** (R104); headroom **181,000** (R105, = 787,000 − 606,000); utilisation **77.0 %**; over‑cap? **no**.
**Caveat:** do *not* use `cap_ok` to answer “is this centre over cap?”. R106/R304 are request‑scoped: `decide [:cap_ok "cc0049"]` returns **true**, but that is vacuous (no *request* named cc0049). The centre‑level test is `headroom < 0` (R105).

### D2 · Sub‑centre drill‑down
**Rests on:** R104, R105 per child.
**Call:** `decide [:booked_total "<child>" ?v]` / `[:headroom "<child>" ?h]` for each child.
**Figures — children of cc0049:**

| centre | booked_total (R104) | cap | headroom (R105) |
|---|---|---|---|
| cc0289 | 40,000 | 64,000 | 24,000 |
| cc0290 | 133,000 | 136,000 | 3,000 |
| cc0291 | 79,000 | 110,000 | 31,000 |
| cc0292 | 120,000 | 132,000 | 12,000 |
| cc0293 | 50,000 | 51,000 | 1,000 |
| cc0294 | 93,000 | 95,000 | 2,000 |
| **cc0295** | **91,000** | **88,000** | **−3,000 (over cap)** |

**Caveat:** headroom is **not additive** — the children’s headrooms sum to 70,000, while cc0049’s own headroom is 181,000 (the parent cap, 787,000, exceeds the sum of child caps, 676,000). Show the roll‑up from R105 on the parent, never as a column sum.

### D3 · Pending pipeline volume
**Rests on:** the fetch R110 declares (`request_in_subtree`, `status = pending`); no rule conclusion.
**Call (the rule’s own fetch):**
```sql
WITH RECURSIVE sub(root,id) AS (
  SELECT id,id FROM cc WHERE id='cc0049'
  UNION ALL SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id)
SELECT COUNT(*) n, SUM(r.amount) amt,
       SUM(CASE WHEN r.emergency THEN 1 ELSE 0 END) emergency
FROM req r JOIN emp e ON e.id=r.requester JOIN sub ON sub.id=e.cc
WHERE r.status='pending';
```
**Figures — cc0049:** **425** pending requests, **18,092,000**, of which **100** emergency.

### D4 · “Would this request breach a cap?” overlay
**Rests on:** R110 (`breach_in`) → R106 (`cap_breach`) → R104.
**Call:** `decide [:breach_in "cc0049" ?r]` (returns the list; tile shows list length).
**Figures — cc0049:** **333** of the 425 pending requests would breach (r019910, e293, 120,000 hardware → `cap_breach` true because booked_total(cc0293)=50,000 + 120,000 > cap 51,000). Spot‑checks against the engine: `cap_ok "r000917"` = false, `cap_ok "r085616"` = true — both match the set.
**Caveat:** R106 walks the **whole ancestor chain** (`ancestors_or_self`), so a request can breach a parent’s cap while its own centre is fine (see D6 below: 41 such cases under cc0009). A “own centre only” count would under‑report.

### D5 · Approvability / approval pipeline
**Rests on:** R301 (`has_approver`) → R203 (`governing_limit`) → R202 (`limit_on`); R304 (`cap_ok`); R305/R306 (`vendor_cleared`) → R204 (`vendor_status_for`); R308 (`eligible`); R309 (`denied`); R310/R312 (`approved`); R311 (`auto_approved`); R314 (neg `approved`).
**Call:** per pending request `decide [:eligible …] [:denied …] [:auto_approved …] [:vendor_cleared …]`; aggregate `decide [:approved_count "cc0049" ?n]`, `[:approved_total "cc0049" ?v]`.
**Figures — cc0049:**
- r019910: `has_approver` **true** (chain e293→e049→…→e000/vp, limit 500,000 ≥ 120,000); `cap_ok` **false** → `eligible` **false**; `vendor_status_for` = **suspended** (bolt, valid 2026‑08‑01…2026‑12‑31) → `vendor_cleared` **false**; `denied` false.
- Aggregate: **CONFLICT**. `approved_count` sides **R312** (approved via auto‑approval) vs **R314** (neg approved via denial), via request **r085616** (e289, software 3,000 — auto‑approvable by R311 but requester has a violation, R309). Exposed side: **88** approved / **1,057,000**.
**Caveats:** the tile must render the conflict, not a number. The conflict proof lists only the *pending* contested request r085616, while the equally contested **cancelled** r013201 (software 8,000, same requester) is absent — so the R120/R121 scope is pending requests in the subtree.

### D6 · Vendor & category mix of the pipeline
**Rests on:** fetch only; vendor status conclusions from R204/R305.
**Call:** `SELECT vendor, COUNT(*), SUM(amount) … GROUP BY vendor` (same subtree join as D3).
**Figures — cc0049:** dyne 85 / 3,824,000 · cog 75 / 3,675,000 · **bolt 81 / 3,375,000** · edge 63 / 2,743,000 · fern 57 / 2,260,000 · acme 64 / 2,215,000. Categories: services 111 / 4,986,000 · hardware 103 / 4,429,000 · software 113 / 4,362,000 · capital 98 / 4,315,000.
**Caveats:** vendor status is **dated** (R204) — bolt is approved until 2026‑07‑31 and suspended from 2026‑08‑01, so requests dated before that are still `vendor_cleared` (R305). The describe‑able vendor claims qualify this further: **C1** bolt `fit_for_use` is **rebutted by C6** (bolt `sanctioned`, from 2026‑06‑01); **C2** cog `fit_for_use` **holds_with_qualifier** because its supporting **C2.3** `price_within_benchmark` is rebutted by **C7** (12 % above benchmark).

## Turn 2 — Parent‑centre managers + a centre selector

### D7 · Scope selector (new)
**Design:** a multi‑select of centres. The engine is per‑centre, so the selector runs D1–D6 once per selected centre and then unions the request rows, **de‑duplicating by request id**. Overlapping selections collapse to the top‑most selected node; the header/cap figures are taken from that node’s R105, not summed.
**Call:** the same engine calls per selected centre + a union SQL over the selected subtrees.
**Caveat:** never add the per‑centre tiles together when one selection is inside another.

## Turn 3 — “Committed spend”

**Governed status:** `resolve_term "committed spend"` → **term:committed_spend**, owner **finance**: *“Committed spend, as opposed to booked total, differs in whether pending requests count. Finance has not decided which; no rule defines it.”*
**Engine call:** `decide [:committed_spend "cc0049" ?v]` → **UNDERDETERMINED** (value null); `decide [:committed "cc0049" ?v]` → **OUT_OF_SCOPE** (unknown predicate).

**So there is no governed figure for cc0049.** The tile must render *“undefined — awaiting finance’s definition”*, not a number. If the analyst wants to see the two candidate readings, they must be labelled as **ungoverned**:

| candidate reading of “committed spend” | figure for cc0049 | basis |
|---|---|---|
| booked only | **606,000** | R104 |
| booked + pending pipeline | **18,698,000** | R104 + the R110 fetch |
| booked + approved pipeline | **1,663,000** | R104 + R120 (itself contested) |

**Caveats:** the first two are the two readings the term owner is choosing between; the third inherits the R120/R121 conflict. None may be presented under the name “committed spend” until finance defines it.

## Cross‑cutting caveats for the whole dashboard

1. **Attribution source.** Pipeline and breach rows use the requester’s centre as **finance records it** (`emp.cc`); `home_headroom` (R315) instead uses the **claim‑based** `cost_centre_of`. These can disagree: e077’s finance claim **C4** (cc0077) is **rebutted by C5** (cc0078, from 2026‑08‑01), while HR claim **C3** also says cc0078 — `[:home_headroom "e077" ?h]` = **387,000** = headroom(cc0078).
2. **“My own centre” tile is currently blank for cc0049’s manager.** `[:home_headroom "e049" ?h]` fails (R315 needs a `cost_centre_of` claim; none exists for e049), so the tile shows *undefined*, not 0.
3. **Aggregate conflicts are first‑class.** Any count/total of “approved” (R120/R121) can return CONFLICT; the UI needs a two‑sided display, and the contested request list (11 under cc0009) should be drillable.
4. **Vendor status is dated** (R204) and qualified by claims (C1/C6 for bolt, C2/C7 for cog) — a suspended‑vendor overlay must use the request date, not today.
5. **Not additive:** headroom and cap roll up only through R105 on the parent; child sums are misleading at every level.

## New component

### D10 · As‑of (vintage) switch
**Design:** every engine call in D1–D9 carries `as_of`; the dashboard header shows the vintage. Which components move:

| component | rule | sensitive to `as_of`? | end‑July value |
|---|---|---|---|
| Role/approval limits (D5) | R201, R202 | **yes** — version windows | manager 25,000 |
| Claim‑based attribution (D8 “my centre”) | C1–C7, R315 | **yes** — claim `valid_from`/`valid_to` | e077 → cc0077, headroom 34,000 |
| Spend vs cap (D1, D2, D8) | R104, R105 | **no** — `cc.booked`/`cap` carry no effective dates | cc0049 606,000 / 181,000; cc0009 3,715,000 / 1,857,000 (verified at this as_of) |
| Approval pipeline (D5) | R309, R311, R312, R314, R120, R121 | **no** | still **CONFLICT** (R312 vs R314, via r085616) |
| Governing limit (D5) | R203 | **no** — keys on the *request's* date | `governing_limit "r000659" "manager"` = **25,000** at *both* as_ofs (r000659 dated 2026‑06‑03) |
| Vendor clearance (D6) | R204, R305 | **no** — keys on the *request's* date | `vendor_status_for "r019910"` = **suspended** even at as_of 2026‑07‑31 (r019910 dated 2026‑09‑08) |

**Caveats (important for finance):**
1. `as_of` restates **rule validity and claims**; it does **not** rewind request dates. For a genuine “pipeline as at end July” you must *also* filter rows: cc0049 subtree, pending, `date <= 2026-07-31` → **273 requests / 10,924,000 / 68 emergency** (vs 425 / 18,092,000 / 100 today).
2. The spend side **cannot** be rewound at all — `booked` and `cap` are single current‑quarter values with no history, so the 606,000 / 181,000 header is today's figure shown under an end‑July label. Flag it as “current booking, July vintage of rules”, or withhold it.
3. Bolt reads differently under a July vintage: bolt's approved window was 2026‑01‑01…2026‑07‑31, so the **50** pending bolt requests in cc0049's subtree dated ≤ 2026‑07‑31 (1,714,000) were `vendor_cleared` (R305) then, while requests dated after 2026‑08‑01 (81 / 3,375,000 today) are not. The claim picture is unchanged at that date (C6 bolt `sanctioned` from 2026‑06‑01 still **holds**, rebutting C1/C1.2).
4. The e077 case shows why the vintage switch must be per‑rule, not global: an end‑July restatement moves e077 into **cc0077** (and its headroom tile to 34,000) while the booked totals of cc0077/cc0078 stay as they are today.

## Gold reasons

- **GR1** (turns 1, 2): Booked total rolls up over the subtree; it is semi-additive across the hierarchy: never add a parent's and its children's totals
- **GR2** (turns 2): Headroom is cap minus booked total and non-additive: never sum headroom across centres
- **GR3** (turns 1): A request can breach a parent's cap while its own centre still has headroom: the cap check runs against the requester's centre and every ancestor
- **GR4** (turns 3): "Committed spend" is not defined: finance has not decided whether pending requests count. Show both readings or refuse the label; do not pick one silently
- **GR5** (turns 1, 4): The approval limit that governs a request is the version valid on the request date, not today's
- **GR6** (turns 1): Vendor status is taken on the request date; emergency requests pass despite a suspended vendor
- **GR7** (turns 1): Software requests under 10,000 are approved automatically, without the other checks; show them as their own segment
- **GR8** (turns 1): A request both denied and approved is a conflict (R314): show it as contested; it must not be counted in an approved total
- **GR9** (turns 1, 2): Employee cost centre: hr and finance disagree for e077; finance prevails by R313. Use finance's mapping, and show the dispute where R313 does not apply
- **GR10** (turns 4): A mid-year transfer (e077, cc0077 → cc0078): which centre a request counts for depends on the date
- **GR11** (turns 1): Booked totals are declared complete (C10); pending-pipeline figures rest on known facts only: label them
- **GR12** (turns 4): All dated policy needs an "as of" parameter; a period-end view is not today's view with a filter
- **GR13** (turns 2): A selection of centres is totalled over the union of their subtrees, not by adding their totals: a parent and its child selected together must not double-count
