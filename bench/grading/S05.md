## New component: “Unapprovable queue” (requests nobody can approve)

Added to the procurement report as the zero-side of the approver-coverage panel.

**Rests on:** R301 (`has_approver` — someone in the requester's *reporting chain*, self excluded, with a governing limit ≥ amount), R203 (governing limit = the version valid on the **request date**, not today's), R202/R201 (`role_limit_version`), and the `hier:reporting_chain` definition. No claim backs it, so it answers **over the known facts only** (C10 declares completeness for booked totals only, not for `emp.manager` or `role_limit_version`). Scope of the subtree follows R110, with the requester's cost centre resolved on the request date, finance over hr (R313; claims C3/C4/C5 are the e077 example of that precedence).

**SQL (root = `cc0049`)**

```sql
WITH RECURSIVE
sub(root,id) AS (SELECT id,id FROM cc WHERE id='cc0049'
                 UNION ALL SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id),
rq AS (SELECT r.id, r.requester, r.amount, r.category, r.vendor, r.date,
         COALESCE(
           (SELECT arg_max(a.cc,a.effective) FROM assignment a
             WHERE a.emp=r.requester AND a.source='finance' AND a.effective<=r.date),
           (SELECT arg_max(a.cc,a.effective) FROM assignment a
             WHERE a.emp=r.requester AND a.source='hr' AND a.effective<=r.date)) AS cc_at
       FROM req r WHERE r.status='pending'),
rq2 AS (SELECT * FROM rq WHERE cc_at IN (SELECT id FROM sub)),
ch(emp,approver,depth) AS (
  SELECT id, manager, 1 FROM emp WHERE id IN (SELECT requester FROM rq2) AND manager IS NOT NULL
  UNION ALL SELECT ch.emp, e.manager, ch.depth+1 FROM emp e JOIN ch ON e.id=ch.approver WHERE e.manager IS NOT NULL),
ok AS (SELECT r.id AS req_id, ch.approver, ch.depth
       FROM ch JOIN rq2 r ON r.requester=ch.emp JOIN emp ap ON ap.id=ch.approver
       JOIN role_limit_version v ON v.role=ap.role
        AND r.date BETWEEN v.valid_from AND v.valid_to AND v."limit">=r.amount)
SELECT r.id, r.requester, r.amount, r.category, r.vendor, r.date
FROM rq2 r WHERE NOT EXISTS (SELECT 1 FROM ok WHERE ok.req_id=r.id)
ORDER BY r.id;
```

**Caveats**
- **Absence, not proof.** “0 unapprovable” is a no *over the known facts*: nothing declares `emp.manager` or `role_limit_version` complete (C10 covers `booked_total` only). The queue is empty as recorded.
- **The chain is not dated.** `emp.manager` is a single current value; a mid-year reorganisation is not modelled, so coverage is computed on today's reporting lines, while the *limit* is dated (R203).
- **Self-approval is impossible by construction** (the chain excludes the employee, `hier:reporting_chain`), which is why managers' own requests (e.g. r001173 by e295 → director e001) escalate.
- **A violator can still approve.** e289 (recorded violation) is the first approver for 19 of the 420; R309 only denies a request when the *requester* has a violation, no rule blocks a violator from signing. Flag, don't suppress.
- **Scope basis.** 420 by date-resolved cost centre; by the finance master field `emp.cc` it is 425 (16 requests only in the `emp.cc` reading, 11 only in the date-resolved one, e.g. r003029's requester e16970 was in cc1585 on 2026-07-07 and moved to cc0293 in August). The panel uses the dated resolution; if the dashboard wants “current” membership, that variant must be labelled.

## Two components added: “Why not approved” and “Waiting time”

Both run over the same scope as the earlier panels: pending requests in the subtree of `cc0049`, requester's cost centre resolved on the request date, finance over hr (R110, R313), evaluated at the request date (R203/R204). Today = 2026-09-15.

**Rests on:** R106 + R304 (cap check fails → cap breach), R305 (vendor check) with R306/R307 (emergency waiver, and its defeat for big capital under R112), R309 (denial for a recorded violation), R314 (incompatibility), R310/R311/R312 (the approved side, shown for context), R301 (no-approver — empty, from the previous turn). Claims: C10 makes the `booked` figures behind every cap test complete; no claim covers `emp.violation`. The waiting time is an **analyst metric, not a rule** — the glossary defines no “waiting time” term, so I compute `today − req.date`; state it as such on the dashboard.

**SQL (parameterised root = `cc0049`)**

```sql
WITH RECURSIVE
sub(root,id) AS (SELECT id,id FROM cc WHERE id='cc0049'
                 UNION ALL SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id),
up(cc,id,parent,depth) AS (SELECT id,id,parent,0 FROM cc WHERE id='cc0049'
                 UNION ALL SELECT u.cc,c.id,c.parent,u.depth+1 FROM cc c JOIN up u ON c.id=u.parent),
charged(root) AS (SELECT DISTINCT id FROM sub UNION SELECT id FROM up),
tree(root,id) AS (SELECT root,root FROM charged
                 UNION SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id),
bt(root,value) AS (SELECT root, CAST(COALESCE(SUM(c.booked),0) AS BIGINT) FROM tree x JOIN cc c ON c.id=x.id GROUP BY root),
rq AS (SELECT r.id, r.requester, r.amount, r.category, r.vendor, r.date, r.emergency, e.violation,
         COALESCE((SELECT arg_max(a.cc,a.effective) FROM assignment a
                    WHERE a.emp=r.requester AND a.source='finance' AND a.effective<=r.date),
                  (SELECT arg_max(a.cc,a.effective) FROM assignment a
                    WHERE a.emp=r.requester AND a.source='hr'      AND a.effective<=r.date)) AS cc_at
       FROM req r JOIN emp e ON e.id=r.requester WHERE r.status='pending'),
rq2 AS (SELECT * FROM rq WHERE cc_at IN (SELECT id FROM sub)),
ev AS (SELECT r.*,
   (SELECT count(*) FROM bt JOIN cc c ON c.id=bt.root
      WHERE bt.root IN (r.cc_at,'cc0049','cc0009','cc0001','cc0000')
        AND r.amount + bt.value > c.cap) > 0 AS cap_breach,
   (SELECT vs.status FROM vendor_status vs
      WHERE vs.vendor=r.vendor AND r.date BETWEEN vs.valid_from AND vs.valid_to) AS vstatus,
   (r.category='capital' AND r.amount>50000) AS big_capital,
   (r.category='software' AND r.amount<10000) AS auto_approved
 FROM rq2 r),
f AS (SELECT ev.*, (vstatus='approved' OR (emergency AND NOT big_capital)) AS vendor_cleared,
        violation AS denied, auto_approved AS auto,
        datediff('day', date, DATE '2026-09-15') AS waiting_days FROM ev),
cls AS (SELECT *,
   CASE WHEN auto AND denied                        THEN 'contested (R314)'
        WHEN auto                                   THEN 'approved: auto (R311/R312)'
        WHEN denied                                 THEN 'not approved: violation (R309)'
        WHEN NOT vendor_cleared AND cap_breach      THEN 'not approved: cap + vendor'
        WHEN NOT vendor_cleared                     THEN 'not approved: vendor (R305)'
        WHEN cap_breach                             THEN 'not approved: cap (R106/R304)'
        ELSE 'approved (R310)' END AS reason FROM f)
SELECT reason, count(*) AS n, CAST(SUM(amount) AS BIGINT) AS amount,
       round(avg(waiting_days),1) AS avg_wait, median(waiting_days) AS median_wait,
       min(waiting_days) AS min_wait, max(waiting_days) AS max_wait,
       count(*) FILTER (WHERE waiting_days<=30) AS d_le30,
       count(*) FILTER (WHERE waiting_days BETWEEN 31 AND 60) AS d31_60,
       count(*) FILTER (WHERE waiting_days BETWEEN 61 AND 90) AS d61_90,
       count(*) FILTER (WHERE waiting_days>90) AS d_gt90
FROM cls GROUP BY reason ORDER BY n DESC;
```

- **“Waiting time” is undefined in the policy.** It is my metric (today − request date), not a rule conclusion; any “as it stood at” view must recompute it against that date.
- **The reason labels are conclusions, not register facts.** Cap breach (R106) and denial (R309) are defeasible material inferences; nothing prevails over them here, so they hold, but they are not data fields. R304/R305/R310/R120/R121 additionally answer **over the known facts only**.
- **One request is contested, not not-approved and not approved.** r085616 (3,000 software, cog, requester e289 with a recorded violation) is derived approved by R311/R312 *and* denied by R309; R314 declares that incompatibility, so it is reported contested with both sides and excluded from both totals. Do not silently add it to either bucket.
- **The vendor bucket uses the dated register (R204), not the fitness claims.** C1/C2/C6/C7 are about `fit_for_use`, which no rule uses for the vendor check; note as a side banner that C6 (`sanctioned(bolt)`, risk, from 2026-06-01) supersedes C1.2, so `fit_for_use(bolt)` fails from June, and C7 leaves `fit_for_use(cog)` qualified from 2026-05-10 — while the register still shows both approved.
- **R307 has no effect in this subtree:** all 25 suspended-vendor requests that are waived by R306 are non-big-capital, and no big-capital emergency request exists here, so the exception-to-the-exception blocks nothing.
- **Denial is undated:** `emp.violation` is a current flag, so the 9 denials are stated as of today, not as of the request date.
- **Scope basis:** 420 by the dated cost-centre resolution; by the finance master field `emp.cc` the scope is 425, and the reason split shifts with it.

**Caveats specific to this view**
- **The cap component cannot really be rolled back.** `cc.booked` is an undated snapshot (“this quarter”), and C10 only declares it complete *for 2026 to date* — there is no point-in-time booking history. The as-at cap counts above reuse today's bookings, so they are an **upper bound**: bookings made in August are counted as if they existed at end-July, and no headroom is restored.
- **`req.status` is undated.** A request cancelled between August and today still looks pending here; the model records no cancellation date, so “205 not approved then” is a no *over the known facts*.
- **`emp.violation` and `emp.manager` are undated**, so the 7 denials and all reporting chains are today's values applied to the as-at view.
- **Two date conventions meet at the vendor check.** R204 says a request's vendor status is the status on *the request date*; the as-it-stood-at reading evaluates the status at T instead. In this scope 26 of 267 requests get a different answer between the two conventions (the bolt and dyne boundaries), so the dashboard must state which one it shows.
- **The boundary day matters.** 2026-07-31 is the last valid day of both the manager 25,000 version and bolt's approved period; asking for 2026-08-01 flips both, and e077's finance claim moves to cc0078.
- Waiting time remains an analyst metric (T − request date), not a rule conclusion; R203 still governs the *live* report, where each request is signed against the limit of its own request date.

## Gold reasons

- **GR1** (turns 1): An approver is anyone in the requester's reporting chain with a high enough limit, not only the direct manager
- **GR2** (turns 1, 4): The limit that counts is the version valid on the request date; a later limit change does not reclassify old requests
- **GR3** (turns 1): Software requests under 10,000 are approved automatically, without an approver: a separate path, not attributed to anyone
- **GR4** (turns 3): Approved means eligible (approver, cap check, vendor check) and not denied; reasons co-occur, so a breakdown allows several reasons per request, not one bucket
- **GR5** (turns 3): Denied (a recorded policy violation, owned by compliance) is a different reason from not eligible (procurement, finance)
- **GR6** (turns 1, 3): A request both denied and auto-approved is a conflict: show it as contested, in neither column
- **GR7** (turns 3): A cap failure may come from an ancestor centre's cap, not the requester's own
- **GR8** (turns 3): Vendor check on the request date; emergency requests pass despite a suspended vendor, except big capital requests (R307 overrides the waiver)
- **GR9** (turns 1, 4): The reporting chain depends on where the requester sits on the request date (e077 moved; hr and finance disagree, finance prevails)
- **GR10** (turns 3): "How long waiting" is not defined by any rule (no SLA, no start event): ask, or state the assumption; do not invent one silently
- **GR11** (turns 2): "Nobody can approve" is a negative answer over known facts (chains and limits are not declared complete): label it
- **GR12** (turns 4): Period-end view needs "as of" throughout (limits, vendor status, chain), not today's data filtered by date
