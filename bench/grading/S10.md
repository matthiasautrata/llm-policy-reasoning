## Turn 1

> Build a vendor-risk view for procurement: which vendors are fit for use, and why. As a worked example, give the standing of fitness for vendors bolt and cog today, and their register status.

## Vendor-risk view — design

One as-at parameter, default today (`2026-09-15`). Fitness and register status are deliberately kept as **two separate components**: the glossary keeps *vendor status* (the dated register entry) apart from *fitness claims*, and no rule derives one from the other.

---

### V1 — Register-status strip (per vendor, as at a date)

**Rests on:** glossary term `vendor_status` (procurement); §3 "a version or status applies on the date it is valid"; R204 (a request's vendor status is the vendor's status on the request date — the same dated join the vendor check R305 uses). No claim needed.

```sql
SELECT vendor, status, valid_from, valid_to
FROM vendor_status
WHERE DATE '2026-09-15' BETWEEN valid_from AND valid_to
ORDER BY vendor;
```

**Figures (2026-09-15):** acme approved, **bolt suspended** (2026-08-01 → 2026-12-31), **cog approved** (2026-01-01 → 2026-12-31), dyne approved, edge approved, fern suspended. Coverage of 2026 is gapless for all six vendors present in `req`.

---

### V2 — Fitness standing (which vendors are fit for use)

**Rests on:** the fitness claims themselves — **C1 / C1.1 / C1.2 / C1.3 / C6** (bolt) and **C2 / C2.1 / C2.2 / C2.3 / C7** (cog), with the claim mechanics of §3: same-asserter later conflicting claim supersedes; a claim whose **required** sub-claim fails fails; a claim whose **supporting** sub-claim fails still holds but is **qualified**. No rule defines `fit_for_use`, so this component is claim-driven only — it must not be merged into V1.

```sql
WITH claims(id, asset, predicate, polarity, asserter, asserted_at, valid_from, valid_to) AS (
  SELECT * FROM (VALUES
    ('C1','vendor:bolt','fit_for_use',1,'procurement',DATE '2026-03-01',DATE '2026-01-01',DATE '2026-12-31'),
    ('C1.1','vendor:bolt','due_diligence_passed',1,'compliance',DATE '2026-02-15',DATE '2026-01-01',DATE '9999-12-31'),
    ('C1.2','vendor:bolt','sanctioned',0,'risk',DATE '2026-02-20',DATE '2026-01-01',DATE '2026-12-31'),
    ('C1.3','vendor:bolt','price_within_benchmark',1,'finance',DATE '2026-02-25',DATE '2026-01-01',DATE '9999-12-31'),
    ('C6','vendor:bolt','sanctioned',1,'risk',DATE '2026-06-03',DATE '2026-06-01',DATE '9999-12-31'),
    ('C2','vendor:cog','fit_for_use',1,'procurement',DATE '2026-03-01',DATE '2026-01-01',DATE '2026-12-31'),
    ('C2.1','vendor:cog','due_diligence_passed',1,'compliance',DATE '2026-02-15',DATE '2026-01-01',DATE '9999-12-31'),
    ('C2.2','vendor:cog','sanctioned',0,'risk',DATE '2026-02-20',DATE '2026-01-01',DATE '2026-12-31'),
    ('C2.3','vendor:cog','price_within_benchmark',1,'finance',DATE '2026-02-25',DATE '2026-01-01',DATE '9999-12-31'),
    ('C7','vendor:cog','price_within_benchmark',0,'finance',DATE '2026-05-10',DATE '2026-05-10',DATE '9999-12-31')
  ) t(id, asset, predicate, polarity, asserter, asserted_at, valid_from, valid_to)
),
win AS (SELECT * FROM claims WHERE DATE '2026-09-15' BETWEEN valid_from AND valid_to),
ranked AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY asset, predicate, asserter ORDER BY asserted_at DESC) AS rn FROM win),
eff AS (SELECT * FROM ranked WHERE rn = 1)
SELECT asset, predicate,
       STRING_AGG(CASE WHEN polarity=1 THEN 'yes' ELSE 'no' END || ' (' || asserter || ')', ', ') AS effective_assertions,
       CASE WHEN COUNT(*) FILTER (WHERE polarity=1) > 0 AND COUNT(*) FILTER (WHERE polarity=0) > 0 THEN 'contested'
            WHEN COUNT(*) FILTER (WHERE polarity=1) > 0 THEN 'holds' ELSE 'fails' END AS standing
FROM eff GROUP BY asset, predicate ORDER BY asset, predicate;
```

**Figures (2026-09-15):**

| asset | due_diligence_passed | sanctioned | price_within_benchmark | fit_for_use |
|---|---|---|---|---|
| vendor:bolt | holds | **holds → "NOT sanctioned" fails** | holds | **fails** (required sub-claim C1.2 superseded by C6) |
| vendor:cog | holds | fails → "NOT sanctioned" holds | **fails** (C2.3 superseded by C7) | **holds, qualified** |

- **bolt: not fit for use.** C1 (procurement, valid 2026-01-01→2026-12-31, in window today) requires C1.1 and C1.2. C1.2 `NOT sanctioned(bolt)` was superseded by risk's later **C6** `sanctioned(bolt)` (asserted 2026-06-03, valid from 2026-06-01, backing "Sanctions list update 2026-06" explicitly supersedes screening S-0220 for bolt). A required sub-claim fails ⇒ C1 fails. C1.3 (supporting) still holds, which does not rescue it.
- **cog: fit for use, qualified.** C2's required sub-claims C2.1 and C2.2 both hold. The supporting sub-claim C2.3 `price_within_benchmark(cog)` (finance, presumably) was superseded by finance's later **C7** `NOT price_within_benchmark(cog)` (asserted 2026-05-10, valid from 2026-05-10, "Benchmark B-19: 12% above"). Supporting failure ⇒ C2 holds but qualified, not clean.

### V3 — "Why" ledger (supersession drill-down)

**Rests on:** same claim ids as V2 plus the §3 supersession rule. This is what makes the badge auditable — each row shows the asserter, window and whether the row is live, superseded or out of window.

```sql
WITH claims(...) AS ( /* same VALUES fixture as V2 */ ),
live AS (SELECT *, (DATE '2026-09-15' BETWEEN valid_from AND valid_to) AS in_window FROM claims),
ranked AS (SELECT id, ROW_NUMBER() OVER (PARTITION BY asset, predicate, asserter ORDER BY asserted_at DESC) AS rn
           FROM live WHERE in_window)
SELECT l.asset, l.id, l.predicate, CASE WHEN l.polarity=1 THEN 'asserts' ELSE 'denies' END AS form,
       l.asserter, l.asserted_at, l.valid_from, l.valid_to, l.in_window,
       CASE WHEN NOT l.in_window THEN 'outside window' WHEN r.rn=1 THEN 'live' ELSE 'superseded' END AS claim_state
FROM live l LEFT JOIN ranked r ON r.id = l.id
ORDER BY l.asset, l.predicate, l.asserted_at;
```

**Figures (2026-09-15):** bolt — C1.1 live (compliance, certainly), C1 live (procurement, presumably), C1.3 live (finance, presumably), **C1.2 superseded**, **C6 live** (risk, certainly). cog — C2.1 live, C2 live, **C2.3 superseded**, **C7 live**, C2.2 live. All ten rows are inside their validity windows, so nothing here fails for window expiry.

---

### V4 — Exposure to unfit / suspended vendors

**Rests on:** glossary `pending exposure` (pending, not cancelled); R204 (the register status attached to a request is the one on the request date); C10 (`complete(booked_total)`) — not used here but it is the only completeness claim in play, and it does not cover this panel's request counts.

```sql
SELECT r.vendor, vs.status AS register_status_on_request_date,
       COUNT(*) AS pending_reqs, SUM(r.amount) AS pending_value
FROM req r
JOIN vendor_status vs ON vs.vendor = r.vendor AND r.date BETWEEN vs.valid_from AND vs.valid_to
WHERE r.status = 'pending' AND r.vendor IN ('bolt','cog') AND r.date <= DATE '2026-09-15'
GROUP BY 1,2 ORDER BY 1,2;
```

**Figures (2026-09-15):** bolt — 6,380 pending requests, 272,714,000 raised while **suspended**; 8,449 / 356,258,000 raised while approved (still "approved" under R204). cog — 15,004 / 636,954,000, all raised while **approved** (cog has no suspended period).

---

### Caveats

- **Fitness ≠ register, and fitness ≠ "qualified supplier".** V1 is a register fact (glossary `vendor_status`); V2 is procurement's claim (glossary `qualified supplier` is a *third*, separate claim family — H-claims — and is not shown here). A suspended entry does not by itself defeat `fit_for_use`, and bolt's failed fitness claim does not alter the register.
- **No precedence orders the asserters** for `sanctioned` or `price_within_benchmark` (contrast G001 for export licences). No cross-asserter conflict arises for bolt or cog — both conflicts are *same-asserter* (risk/risk, finance/finance) and resolve by supersession. Had the conflicting claims come from different asserters, the standing would be **contested**, and the dependent fitness claim contested too.
- **Both standings are determinate today**, not contested: bolt fails, cog holds-qualified. V2/V3 do not rest on absence from the data, so the "no completeness claim" limit does not bite here; but for any vendor with no live `fit_for_use` claim the badge would read "no known claim", i.e. a no over the known facts, because nothing declares the claims ledger complete (C10 covers booked totals only).
- **Claims are not in the database.** V2/V3 need the fixture above (or a `claim` table); only V1 and V4 read live tables. If the fixture is not maintained, the view silently shows stale supersessions.
- **Window lapse:** C1 and C2 are valid only to 2026-12-31 — after that both vendors would drop to "no known claim" without any new assertion.
- **V4 is context, not a verdict.** Requests raised while a vendor was approved keep that status under R204 even if the vendor is suspended today; the panel is a queue for re-review, not a list of invalid requests (request-level validity is the R305/R308/R310 chain, a different view).

## Turn 2

> Why is cog flagged? Name the claims involved.

## Why cog is flagged

Cog carries the **"fit for use — qualified"** badge, not a failure. The flag is raised by the **supporting** sub-claim of procurement's fitness claim, and it is raised by exactly one claim pair.

**Claims involved**

| id | statement | asserter | asserted at | valid | qualifier | state today (2026-09-15) |
|---|---|---|---|---|---|---|
| **C2** | `fit_for_use(cog)` | procurement | 2026-03-01 | 2026-01-01 → 2026-12-31 | presumably | **live — holds, qualified** |
| C2.1 | `due_diligence_passed(cog)` | compliance | 2026-02-15 | 2026-01-01 → open | certainly | live — holds (required) |
| C2.2 | `NOT sanctioned(cog)` | risk | 2026-02-20 | 2026-01-01 → 2026-12-31 | certainly | live — holds (required) |
| **C2.3** | `price_within_benchmark(cog)` | finance | 2026-02-25 | 2026-01-01 → open | presumably | **superseded** (supporting) |
| **C7** | `NOT price_within_benchmark(cog)` | finance | 2026-05-10 | 2026-05-10 → open | certainly | **live — the flag** |

**Mechanism (in the order it applies)**

1. C2 declares C2.1 and C2.2 as **required** and C2.3 as **supporting** (its link field: "requires C2.1, C2.2; supported by C2.3").
2. The two required sub-claims both hold — C2.1 (compliance) and C2.2 (`NOT sanctioned`, risk) are live today. So C2 is **not defeated**.
3. C2.3 fails: finance asserted **C7** on 2026-05-10 (backing "Benchmark B-19: 12% above", certainly, valid from 2026-05-10), denying the same predicate. Same asserter, later, conflicting ⇒ under §3 C7 **supersedes** C2.3. Both rows are inside their validity windows, so this is supersession, not window expiry.
4. A **supporting** sub-claim that fails does not kill the parent: C2 still holds, but it is **qualified** — that is the flag. (Contrast bolt, where the superseded claim C1.2 was a *required* sub-claim, so C1 **fails** outright.)

**Not the cause:** cog's register status is **approved** for the whole of 2026 (V1) — the flag is not a register suspension; and there is no sanctions issue for cog (C2.2 is live and unopposed, unlike bolt's C1.2 vs C6).

**Dated detail:** the flag starts on **2026-05-10** — C7's valid-from date, which is also its assertion date. Before that date C2.3 held and cog's fitness was clean; the "why" ledger (V3) should therefore be read as-at, and a back-dated view of cog before 2026-05-10 shows no flag.

**Caveat:** this is same-asserter supersession (finance over finance), so it resolves without any precedence rule — the standing is determinate, not contested. Had the denial of `price_within_benchmark(cog)` come from a *different* asserter, no rule orders asserters for that predicate, so the sub-claim would be **contested** and C2 would be contested as well.

## Cog's flag — asserter and dates, claim by claim

Two dates matter per claim and they are different: **asserted at** = when the asserter said it; **valid from** = since when it applies. Claims here are backdated, so "since when" is the *valid-from* date, not the assertion date. (Open-ended windows are shown as `null` / "open".)

| id | statement | who (asserter) | asserted at | valid from | valid to | status today | backing |
|---|---|---|---|---|---|---|---|
| **C7** | `NOT price_within_benchmark(cog)` | **finance** | **2026-05-10** | **2026-05-10** | open | **live — carries the flag** | Benchmark B-19: 12% above |
| C2.3 | `price_within_benchmark(cog)` | **finance** | 2026-02-25 | 2026-01-01 | open | superseded by C7 (was effective 2026-01-01 → 2026-05-09) | Benchmark B-12: within 5% |
| **C2** | `fit_for_use(cog)` | **procurement** | 2026-03-01 | 2026-01-01 | 2026-12-31 | live — holds, qualified | Vendor onboarding file VO-21 |
| C2.1 | `due_diligence_passed(cog)` | **compliance** | 2026-02-15 | 2026-01-01 | open | live — holds (required) | KYC review 2026-02 |
| C2.2 | `NOT sanctioned(cog)` | **risk** | 2026-02-20 | 2026-01-01 | 2026-12-31 | live — holds (required) | Sanctions screening run S-0220 |

**The short answer**

- **Who says so:** **finance**, and only finance — C7 is the claim that raises the flag, and C2.3 is finance's own earlier, now-superseded claim. No other asserter is involved in cog's flag.
- **Since when:** **2026-05-10** — C7's valid-from date, which is also the day finance asserted it. That is **128 days** before today (2026-09-15).
- The parent claim C2 is **procurement's**, asserted 2026-03-01, valid 2026-01-01 → 2026-12-31: procurement's "fit for use" has been in force 257 days and still holds — it is only *qualified*, because finance's supporting price claim lapsed on 2026-05-09.

**Reading the window correctly**

- C2.3 and C7 are both finance's and cover the same predicate, so this is **same-asserter supersession**: C2.3 was effective 2026-01-01 → 2026-05-09, C7 from 2026-05-10. Before 2026-05-10 the supporting sub-claim held, so an as-at view of cog dated 2026-05-09 shows **no flag**.
- The required sub-claims (C2.1 compliance, C2.2 risk) both date from **2026-01-01** by validity, though they were only asserted in mid/late February — so the "since when" column and the "asserted at" column must both be shown, or the audit trail is misleading.
- **Expiry:** C2 and C2.2 lapse on **2026-12-31** (no 2027 version exists). From 2027-01-01, cog's fitness would read as "no known claim" over the known facts, not as a renewal.

**Context (for contrast):** bolt's failure is carried by **risk** — C6 `sanctioned(bolt)` asserted 2026-06-03, valid from 2026-06-01 (106 days), superseding risk's own C1.2 — while bolt's **register suspension** is a table fact with no asserter at all (`vendor_status`: suspended 2026-08-01 → 2026-12-31, 45 days). So the two vendors' flags differ in asserter (finance vs risk), in kind (claim vs register), and in date (2026-05-10 vs 2026-06-01/2026-08-01).

### Caveats

- **The reading is undecided, not the data.** §3 makes a view "as it stood at" a date evaluate dated rules, statuses and claims *at that date*, which points to reading A; the phrase "what we knew" points to reading B (assertion date). Nothing in the rules defines which governs, so the bolt badge must be shown as two-valued (or the user must pick) — do not silently choose one, and do not call it contested: contested is for opposing claims from different asserters, which this is not.
- **Register and fitness still do not interact.** At 2026-06-02 both vendors were register-approved; bolt's register suspension (2026-08-01) and C6's assertion (2026-06-03) both lie after the date, and neither is derivable from the other.
- **One-day sensitivity.** The bolt fork closes on 2026-06-03; any as-at date from 2026-06-01 to 2026-06-02 forks, and from 2026-06-03 both readings agree bolt fails. Today (2026-09-15) they also agree, so the divergence is confined to that window.
- **Same-asserter supersession throughout**, so no precedence rule (G001-style) is invoked; a cross-asserter conflict on `sanctioned` or `price_within_benchmark` would be contested, since no rule orders asserters for those predicates.
- **Absence:** nothing at this date declares the claims ledger complete — C10 covers booked totals only — so any "no claim" row is a no over the known facts.

## Gold reasons

- **GR1** (turns 1): Fit for use is procurement's claim, resting on required sub-claims (due diligence, not sanctioned) and a supporting one (price within benchmark)
- **GR2** (turns 1, 2): A failing required sub-claim rebuts fitness; a failing supporting one only qualifies it
- **GR3** (turns 3): Each sub-claim has its own asserter (compliance, risk, finance) and validity; report them per claim, not under procurement
- **GR4** (turns 2, 4): cog: finance's later claim (C7, from 10 May) that the price is not within benchmark supersedes its earlier C2.3 (same asserter, later wins): fitness is qualified from that date
- **GR5** (turns 1, 4): bolt: risk's later claim (C6, sanctioned, from 1 June) supersedes its earlier C1.2: fitness rebutted from that date
- **GR6** (turns 2): Later wins only within one asserter; between different asserters a disagreement stays contested unless superiority is stated
- **GR7** (turns 1): Validity windows end (C1, C2 to 31 Dec): fitness expires; it is not permanent
- **GR8** (turns 4): "What we knew at <date>" (assertion and recording time) differs from "what held at <date>" (valid time): two axes, two views
- **GR9** (turns 1): Vendor status (register) is distinct from fitness claims: a vendor can be approved in the register yet not fit, and the reverse
