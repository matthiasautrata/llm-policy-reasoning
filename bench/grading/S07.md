## Turn 2 — component: “Unapprovable requests” (no eligible approver)

This is a drill‑down of the turn‑1 **Approval routing** component. It answers the literal question *“who can approve this request?”* by returning the pending requests for which the answer is **nobody** — i.e. `has_approver = false`.

### What the component is
A filtered list (and a count KPI) of pending requests where no member of the requester’s reporting chain has a governing approval limit ≥ the amount. It is the complement of the routing table: routing shows *the* approver; this tile shows the rows where routing finds none.

### Rules / claims it rests on
- **R301** `has_approver ?r` — ∃ approver in the requester’s reporting chain whose governing limit ≥ amount. This is the predicate the tile evaluates (nothing is re‑derived in SQL).
- **R203** `governing_limit ?r ?role ?l` (the limit of a chain member’s role *as at the request date*), which rests on **R202** `limit_on ?role ?d ?l` ← **R201** `role_limit ?role ?l` and the `role_limit_version` table.
- Data binding **`reporting_chain`** (recursive manager walk) and **`request_in_subtree`** (recursive cost‑centre walk) — concepts, not rules.
- No claims (C…) are involved in this component; the vendor/employee claims (C1…C7) belong to the turn‑1 *Block‑reasons* component.

### Engine call it runs
Per request: `decide [:has_approver "r…"]` (or `why` for the witness). Example witnesses:
- `[:has_approver "r001405"]` → **true** (120 000, analyst, cc0291) — witness: VP, governing_limit = 500 000 ≥ 120 000 (R301 via R203/R202).
- `[:has_approver "r028134"]` → **true** (90 000, senior_manager, cc0049).
- `[:has_approver "r004511"]` → **true** (90 000, cc0289, requester has a policy violation — the violation affects *denied* (R309), not approver existence).

Scope query (the `request_in_subtree` concept) that feeds the tile:

```sql
WITH RECURSIVE sub(root,id) AS (
  SELECT id,id FROM cc WHERE id='cc0049'
  UNION ALL SELECT s.root,c.id FROM cc c JOIN sub s ON c.parent=s.id)
SELECT r.id, r.requester, e.cc, r.amount
FROM req r JOIN emp e ON e.id=r.requester JOIN sub ON sub.id=e.cc
WHERE r.status='pending';           -- 425 rows
```

### Figures for the worked example (pending requests of cc0049 + subtree)
- Pending requests in scope: **425** (cc0049 alone: 8; children cc0289–cc0295: 417).
- Requests nobody can approve (`has_approver = false`): **0**.
- cc0049 alone: **0 of 8**. Largest amount in scope: **120 000** (e.g. r001405, r002063, r002791).

### Caveats
- **It is empty by construction, not by accident.** Every requester’s chain terminates at the VP, whose limit is 500 000 for the whole of 2026 (R201/R202), and no request in scope exceeds 120 000. The tile therefore reports an absence‑based result — the engine qualifies such answers as *“total over known facts in declared scope.”* It would only become non‑empty if a requester had no manager (only **e000/vp** has none, and the VP has raised no requests) or if an amount exceeded 500 000.
- **`has_approver` is existential.** It says *some* chain member can approve; it does **not** name the nearest/most‑junior one. “Who can approve” in the routing table should be presented as the least‑depth qualifying approver (a presentation choice over the `reporting_chain` + `governing_limit` data), while this tile only tests existence.
- **Not the same as “blocked.”** A request can have an approver and still not be approved (denied R309/R314, cap breach R106/R304, vendor not cleared R204/R305–R307). Those belong to the turn‑1 *Block‑reasons* component; don’t merge the two tiles or the zero here will be misread.
- Amounts and role limits are date‑effective: the tile must evaluate `has_approver` at the request’s own date (R202/R203), not at “today”.

### Caveats
- **Reasons overlap.** 333 rows breach a cap but only 312 are *primarily* cap‑breach (the rest are also denied or auto‑approved); 89 rows have a suspended vendor but only 15 are primarily that (the rest also breach caps or are auto‑approved). Show one primary reason plus flag chips, and never sum the flag column as if exclusive.
- **Auto‑approval bypasses the other checks.** R311/R312 approve *any* software < 10 000 regardless of cap or vendor: 30 rows, some of which breach caps or use suspended vendors, are nonetheless “approved”. The single **contested** row (r085616: software 3 000, requester e289 has a violation) is R312 vs R314 — the tile must surface the conflict, not pick a side.
- **Emergency overrides.** R306 makes emergency requests vendor‑cleared, and R307 takes it back only for emergency **and** suspended **and** big‑capital (>50 000 capital). So r028134 (emergency, *bolt*, 90 000) is cleared while r000002 (emergency, *fern*, big‑capital) is not.
- **Aging is a data field**, not a rule; recompute against the dashboard’s as‑of date.
- **Provenance.** The per‑row verdict is the engine call listed; the worked‑example totals were produced by evaluating those same rule conditions in bulk over the 425‑row scope (SQL mirroring R106/R204/R301/R304/R305/R306/R307/R308/R309/R310/R311/R312/R314), because the engine answers one request at a time. Spot‑checks against `decide` agree: r004511 denied+not‑approved, r085616 CONFLICT, r060739 vendor‑not‑cleared, r000917 cap‑breach. No **claims** (C…) are used here — the vendor claims C1–C7 (sanctioned/due‑diligence/benchmark) are not referenced by the approval rules.

## Gold reasons

- **GR1** (turns 1): An approver is anyone in the requester's reporting chain with a high enough limit, not only the direct manager
- **GR2** (turns 1, 4): The limit that counts is the version valid on the request date; a later limit change does not reclassify old requests
- **GR3** (turns 1): Software requests under 10,000 are approved automatically, without an approver: a separate path, not attributed to anyone
- **GR4** (turns 3): Approved means eligible (approver, cap check, vendor check) and not denied; reasons co-occur, so a breakdown allows several reasons per request, not one bucket
- **GR5** (turns 3): Denied (a recorded policy violation, owned by compliance) is a different reason from not eligible (procurement, finance)
- **GR6** (turns 1, 3): A request both denied and auto-approved is a conflict: show it as contested, in neither column
- **GR7** (turns 3): A cap failure may come from an ancestor centre's cap, not the requester's own
- **GR8** (turns 3): Vendor check on the request date; emergency requests pass despite a suspended vendor, except big capital requests (R307 overrides the waiver)
- **GR9** (turns 1, 4): The reporting chain depends on where the requester sits on the request date (e077 moved; hr and finance disagree, finance prevails)
- **GR10** (turns 3): "How long waiting" is not defined by any rule (no SLA, no start event): ask, or state the assumption; do not invent one silently
- **GR11** (turns 2): "Nobody can approve" is a negative answer over known facts (chains and limits are not declared complete): label it
- **GR12** (turns 4): Period-end view needs "as of" throughout (limits, vendor status, chain), not today's data filtered by date
